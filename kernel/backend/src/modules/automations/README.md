# Automations

Automation triggers record participating policies and after hooks. Request triggers retain normalized command drafts when policies match; change triggers retain exact before/after snapshots when after hooks match. Signal triggers retain emitted payloads and recipients; provider-import completion triggers retain provider identity when hooks match. Mutation receipts own committed command results and dispatch references independently of trigger retention. A repeated command identity returns its recorded result without reapplying a write or selecting hooks from the current catalog.

## Planning And Execution

Owning services commit the source write, its receipt, and matching pinned after-hook runs in one transaction; sandbox work starts only after commit. Before-policy hooks run in deterministic order outside the transaction before the source write, cannot perform mutations, and may accept, reject, or transform the command draft. A matching change trigger links to an actual request trigger when one exists. After hooks run independently, so one failure does not roll back committed source data or prevent sibling hooks. A write without matching hooks leaves no automation snapshots or dummy parent trigger.

Each run pins the exact sandbox script, its input projection, plugin revision, and plugin configuration revision accepted during planning. Kernel runs pin a source-zero script and use null plugin/configuration revisions. The workflow claims numbered attempts, derives a deterministic invocation from the complete retained trigger and the pinned projection, executes the exact pin, and records bounded logs, errors, timing, and output. Plugin upgrades, disablement, and uninstall affect future planning but do not change accepted runs during their retry window.

`LifecyclePlanner.plan` runs on the caller's active transaction and returns either `NoHooks` or a persisted trigger with ordered pinned runs and policy declarations from pinned revisions. Callers resolve signal audiences and supply recipients; the planner deduplicates the actor. A caller inspects a persisted request trigger's `blockedReason`: a blocked request must reject the write, while blocked post-write planning produces a warning only when `hasRequiredHooks` is true. Callers execute the returned policies sequentially after the planning transaction commits and submit after-hook runs only after the source commit.

The automations feature Layer constructs the planner with its resolver, run repository, and trigger repository. The planner implementation keeps those collaborators as constructor requirements; transaction-scoped catalog reads use the same resolver instance throughout a plan.

Batch owners pass identities already processed for the current entity as `excludedOncePerSubjectPolicies`, keyed by the run's stable `pluginId`/`hookSlug` and the batch's deterministic subject key. Before-event `once-per-subject` hooks are excluded before budget counting and insertion; participating request triggers retain the normalized exclusions.

Before its first write, a logical batch records its applicable batch-hook candidates (including an empty decision) and pins their revisions and scripts. Only batches with candidates retain committed item change evidence in receipts. Sealing creates matching immutable batch triggers and runs, then removes temporary evidence and candidate pins atomically. A batch hook receives all changed items in its scope/resource chunk, even when only some match its targets; its projection filters the received items. Item hooks (`frequency` omitted or `"item"`) match only non-batch triggers and batch hooks match only batch triggers. `executionScope` is compared against the run's `executionUserId`, not the trigger's scope user.

`LifecyclePlanner.planBatch` groups committed evidence by scope user and chunks it in item order by both `AUTOMATIONS_BATCH_MAX_ITEMS` and the batch payload byte budget. It derives each chunk's trigger from the write identity and chunk index. Invocation preparation applies the pinned run projection and enforces the 64 KiB sandbox context limit. Batch sealing happens in a transaction; callers dispatch item runs before batch runs. An explicitly cancelled event workflow seals its committed prefix, leaving queued batch runs for reconciliation; suspension leaves the batch resumable. Prepared-persist APIs (`persistPreparedUpdate`, `persistPreparedUserCreate`, and their siblings) return item dispatch references only; the service owning a multi-item write seals one batch per resource.

Planning takes the per-plugin configuration lock in shared mode, because it only reads the pointers it pins; configuration writers take the same key exclusively. The root advisory budget lock applies when matching automation work is admitted, not for a no-hook write. The resolver caches locked catalogs within a transaction. The trigger repository persists a participating trigger's final decision once, before any recipients or runs, in the same transaction.

Retry policy belongs to the pinned after hook. Only classified infrastructure failures retry automatically, and external HTTP hooks require explicit run-ID idempotency. A workflow waiting on required hooks or a before-policy submits only runs that were never claimed, so replays do not resubmit, and awaits only runs that were claimed or submitted by it. It races their exits against one durable clock at its journaled absolute deadline, stops awaiting the losing clock, then records the outcome once from the attempt rows (finished before the deadline or not), so the outcome does not depend on which side woke it. Callers outside a workflow re-read the attempts every 50 ms until the deadline. The frequent reconciler claims due queued runs; manual retry revalidates ownership, attempt count, retention, and artifacts before queueing another attempt. Before-policy failures never retry. Missing retained evidence, a missing or incompatible projection, non-JSON projected data, projected input over 64 KiB, and projected-schema failure all fail closed with bounded preparation diagnostics. User history exposes bounded, redacted trigger/run/attempt detail without script source, encrypted configuration, or cross-user payloads.

## Causation And Limits

Every trigger carries an initiator, source, execution ID, root execution ID, depth, optional parent trigger, and optional parent run. Automation host mutations derive this context from the trusted run; plugin input cannot choose its parents. Command request and committed change triggers retain their direct link, while both remain attributed to the parent run. The root budget blocks descendants beyond the configured depth or run count and records omitted hooks without executing them.

Notification subscriptions remain user configuration. A signal trigger snapshots its recipient set, then creates at most one run for each matching user/hook pair. Provider-import completion uses the same trigger, run, attempt, causation, retry, and history model as entity, event, relationship, and signal operations.

Retained triggers remain complete immutable evidence for participating hooks; projection narrows only the sandbox invocation. RyotQL exposes current state only and cannot reconstruct trigger-time evidence. Later updates, deletion, or plugin changes must not alter accepted execution input. Pending batch candidates keep executable/configuration pins until sealing. Receipts remain while their owning execution can replay; no independent receipt TTL exists without an authoritative execution-retirement signal. Portable backups exclude receipts and pending batch evidence. Automation-history pruning can remove sensitive attempt detail and expired executable material without removing command replay results or event write counts.

User-owned commands and sandbox subjects carry the exact user ID and a random database-owned account-generation token. Admission checks this token and account retirement under the account row lock on replay reads and committing writes. Workflow-owner receipts record the actual workflow name and execution ID before dispatch. Account reset closes admission and retires those owners before deleting receipts; recreating the same user ID issues a different token. User bootstrap and user-driven population execution IDs include the generation.
