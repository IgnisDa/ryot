# Automations

Automation triggers record participating after hooks. Change triggers retain exact before/after snapshots when after hooks match. Signal triggers retain emitted payloads and recipients; provider-import completion triggers retain provider identity when hooks match. Policies persist nothing: they have no trigger, run, attempt, or job rows.

## Planning And Execution

Owning services commit the source write and matching pinned after-hook runs in one transaction; sandbox work starts only after commit. Policies (before hooks) run in deterministic order before the source write, cannot perform mutations, and may accept, reject, or transform the command draft. After hooks run independently, so one failure does not roll back committed source data or prevent sibling hooks. A write without matching hooks leaves no automation snapshots or dummy parent trigger.

Each run pins the exact sandbox script, its input projection, plugin revision, and plugin configuration revision accepted during planning. Kernel runs pin a source-zero script and use null plugin/configuration revisions. A job claims numbered attempts, derives a deterministic invocation from retained evidence and the pinned projection, executes the exact pin, and records bounded logs, errors, timing, and output. After hooks have no write host capabilities: a hook returns `{ changes? }`, and a succeeded attempt commits them through `ScriptChanges` in the same transaction that finalizes it. The attempt row is the receipt: the commit first locks the run and stops if the attempt is already settled, so a retried or concurrent execution of the same attempt never commits twice. Signals and notifications are the change set's `signals` and `notifications`. A change set that conflicts with a newer write, or whose policy could not run, fails the attempt as `resource-unavailable` (retryable); a policy rejection or a refusal as `business-failure`; an invalid change set as `invalid-output`. Compatible upgrades do not change accepted pins. Current account and installation authority still applies; unavailable or quarantined installations fail with a typed boundary reason without replacing code or deleting history.

`LifecyclePlanner.plan` runs on the caller's active transaction and returns either `NoHooks` or a persisted trigger with ordered pinned after-hook runs. Callers resolve signal audiences and supply recipients; the planner deduplicates the actor. A trigger over the root budget records its omitted hooks in `blockedReason` and queues no runs; the source write still commits. Callers dispatch after-hook runs only after the source commit.

A `PolicyRequest` (`lifecycle/policies.ts`) is the in-memory description of the writes one policy call decides: their resource, scope user, causation, time, entity references, and each item's request payload. It is never stored. `LifecyclePolicies.match` resolves a request's matching policies on the caller's transaction under the catalog lock, ordered by position, plugin, and hook slug; each match carries its plugin, configuration, and script pins. `LifecyclePolicies.run` calls one policy once with every item it targets: it pins the script for a `before`-stage `automation-run` subject, which names no run or trigger, prepares the invocation from the pinned script and projection in a short transaction of its own, runs it through `ScriptCalls` on the request's lane, and requires the output to decide each item exactly once. Items the policy does not target get no decision. A policy failure (no valid pin, declaration, invocation or output, or a failed run) is `AutomationPolicyExecutionError` carrying its sandbox failure kind, while a database failure while preparing it propagates as itself. Owning services share one adapter: `matchPolicies` chunks a batch and matches each chunk on the commit transaction, `applyPolicies` calls each chunk's policies in order with the items earlier policies left active and classifies a failure as `PolicyUnavailable` (a run that failed with `resource-unavailable`, `timeout` or `infrastructure`, which callers retry) or `PolicyRejected` with `policy-execution-failed`, and `acceptedPolicyRequests` gives each item its accepted request or fails it with `PolicyRejected`. The commit never retries a policy failure itself.

Signals are written only as a change set's `signals` part, which `SignalEmissionService.planSignal` plans in the commit transaction. `KernelSignals.commit` commits one signal the kernel emits under a user's principal and its own command; durable callers run it in an activity. An optional ledger makes it conditional: its `check` is the commit's precondition, and its `record` stores the planned trigger in the commit transaction, which fails instead when the trigger was blocked, so the ledger tries again. Due reminders, signal schedule deliveries and disabled integrations emit their signals through it.

`LifecyclePlanner.planChanges` plans committed change triggers together: it plans each trigger, then runs `LifecycleWork.admit` and `LifecycleWork.derive` once for the list. Derivation returns the writes plugins declare, such as membership rules; those writes join the source transaction and their triggers are planned the same way. The result holds one list of dispatch plans per trigger, with admitted job IDs and derived plans on the first, since a chunk's writes commit together. `planChange` is the one-trigger case.

The automations feature Layer constructs the planner with its resolver, run repository, and trigger repository. The planner implementation keeps those collaborators as constructor requirements; transaction-scoped catalog reads use the same resolver instance throughout a plan.

A `once-per-subject` event policy receives at most one item per subject in each call. Batch owners keep a subject's items in one policy chunk, so it runs once per subject.

A logical batch opens, records its changes and seals inside one transaction. Before its first write it resolves its applicable batch-hook candidates and pins their revisions and scripts in that transaction's memory. Only batches with candidates keep committed item change evidence. Sealing creates matching immutable batch triggers and runs before the transaction commits. A batch hook receives changed items belonging to its exact definition owner in its scope/resource chunk, even when only some match its local targets. Its pinned projection selects properties. Item hooks (`frequency` omitted or `"item"`) match only non-batch triggers and batch hooks match only batch triggers. `executionScope` is compared against the run's `executionUserId`, not the trigger's scope user.

`LifecyclePlanner.planBatch` groups committed evidence by scope user and chunks it in item order by both `AUTOMATIONS_BATCH_MAX_ITEMS` and the batch payload byte budget. It derives each chunk's trigger from the write identity and chunk index. Invocation preparation applies the pinned run projection and enforces the 64 KiB sandbox context limit. Callers dispatch item runs before batch runs. Prepared-persist APIs (`persistPreparedDelete`, `persistPreparedUserCreate`, and their siblings) return item dispatch references only; the service owning a multi-item write seals one batch per resource.

Planning takes the per-plugin configuration lock in shared mode, because it only reads the pointers it pins; configuration writers take the same key exclusively. The root advisory budget lock applies when matching automation work is admitted, not for a no-hook write. The resolver caches locked catalogs within a transaction. The trigger repository persists a participating trigger's final decision once, before any recipients or runs, in the same transaction.

Retry policy belongs to the pinned after hook. Only classified infrastructure failures retry automatically, and external HTTP hooks require explicit run-ID idempotency. Each attempt is one `automation-run` job, keyed by its attempt identity and enqueued in the transaction that admits the account, so replays and repeated submissions cannot queue it twice. After the source commit, dispatch queues each run that was never claimed as its first attempt's job; no caller waits for after hooks. The frequent reconciler claims due queued runs. Runs are queued at planning time, so a first attempt is reconciled only after its commit has had a sandbox timeout to dispatch it. Missing retained evidence, a missing or incompatible projection, non-JSON projected data, projected input over 64 KiB, and projected-schema failure all fail closed with bounded preparation diagnostics. Execution records remain internal; there is no history page, manual retry API, or RyotQL catalog access to them.

## Causation And Limits

Every trigger carries an initiator, source, execution ID, root execution ID, depth, optional parent trigger, and optional parent run. Changes an after hook returns derive this context from the trusted run: they commit under `automationLifecycleCausation` with the attempt's execution ID, so the triggers they cause are planned and budgeted as the run's children; plugin input cannot choose its parents. The triggers they cause link to the run's trigger as their parent trigger. The root budget blocks descendants beyond the configured depth or run count and records omitted hooks without executing them.

Notification subscriptions remain user configuration and select an exact plugin/kernel owner plus local signal slug. Formatter hooks resolve within that owner. A signal trigger snapshots its recipient set, then creates at most one run for each matching user/hook pair. Entity, event, relationship and provider-import evidence carries the stored schema owner; event matching also includes its parent entity schema. Provider-import completion uses the same trigger, run, attempt, causation, retry, and history model as domain mutations.

User-scoped after hooks may explicitly observe kernel collection `review`, `add-entity-to-collection`, and `remove-entity-from-collection` events with a kernel-owned target. Before policies remain local to their plugin, and global kernel observers are not allowed. Matching requires kernel event and parent ownership, not the name `collection`; a plugin may independently declare that same local name. Retained runs use their captured targets. Observation does not change the executing plugin's domain-write principal; kernel collection writes still require the existing explicit collection capability.

Retained triggers remain complete immutable evidence for participating hooks; projection narrows only the sandbox invocation. RyotQL exposes current state only and cannot reconstruct trigger-time evidence. Later updates, deletion, or plugin changes must not alter accepted execution input. Automation-history pruning can remove sensitive attempt detail and expired executable material without removing event write counts.

User-owned commands carry the account's user ID. Admission checks account retirement under the account row lock on committing writes. Workflow executions record the account they work for at admission. Account reset closes admission, interrupts those executions, and deletes the account's jobs, workflow executions, and idempotency keys, so a recreated account can run the same deterministic executions again.
