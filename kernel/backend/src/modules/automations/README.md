# Automations

Automation triggers record participating policies and after hooks. Request triggers retain normalized command drafts when policies match; change triggers retain exact before/after snapshots when after hooks match. Signal triggers retain emitted payloads and recipients; provider-import completion triggers retain provider identity when hooks match.

## Planning And Execution

Owning services commit the source write and matching pinned after-hook runs in one transaction; sandbox work starts only after commit. Before-policy hooks run in deterministic order outside the transaction before the source write, cannot perform mutations, and may accept, reject, or transform the command draft. A matching change trigger links to an actual request trigger when one exists. After hooks run independently, so one failure does not roll back committed source data or prevent sibling hooks. A write without matching hooks leaves no automation snapshots or dummy parent trigger.

Each run pins the exact sandbox script, its input projection, plugin revision, and plugin configuration revision accepted during planning. Kernel runs pin a source-zero script and use null plugin/configuration revisions. The workflow claims numbered attempts, derives a deterministic invocation from retained evidence and the pinned projection, executes the exact pin, and records bounded logs, errors, timing, and output. Compatible upgrades do not change accepted pins. Current account and installation authority still applies; unavailable or quarantined installations fail with a typed boundary reason without replacing code or deleting history.

`LifecyclePlanner.plan` runs on the caller's active transaction and returns either `NoHooks` or a persisted trigger with ordered pinned runs and policy declarations from pinned revisions. Callers resolve signal audiences and supply recipients; the planner deduplicates the actor. A caller inspects a persisted request trigger's `blockedReason`: a blocked request must reject the write, while blocked post-write planning produces a warning only when `hasRequiredHooks` is true. Callers execute the returned policies sequentially after the planning transaction commits and submit after-hook runs only after the source commit.

`LifecycleExecution.executePolicy` and `executeBatchPolicy` first run the policy's first attempt directly through `DirectPolicyAttempts`: claim, prepare, one sandbox run through the inline host, and finalize, with no `AutomationRunWorkflow` or `ScriptExecutionWorkflow`. Inside a workflow the attempt is a journaled activity, so replay never takes a different path. The direct run waits at most 1 s for sandbox admission, because a parked isolate keeps its lease and two parents waiting on each other's leases would deadlock. When it cannot get a lease, or the script reaches a host call only the replay loop settles, it raises `DirectScriptDeferred`: the attempt releases its claim, returning the run to queued with no attempt row, and the policy dispatches as before. Inside a workflow a claimed run is executed rather than skipped, which takes over a claim left by a direct attempt whose process died. The runtime installs the attempt once the sandbox exists; migrations and tests leave `DirectPolicyAttempts` empty, so every attempt defers. An event create that matches policies runs them as request work and records policy failures, blocked batches, and persist conflicts in its outcomes.

`LifecyclePlanner.planChanges` plans committed change triggers together: it plans each trigger, then runs `LifecycleWork.admit` and `LifecycleWork.derive` once for the list. Derivation returns the writes plugins declare, such as membership rules; those writes join the source transaction and their triggers are planned the same way. The result holds one list of dispatch plans per trigger, with admitted job IDs and derived plans on the first, since a chunk's writes commit together. `planChange` is the one-trigger case.

The automations feature Layer constructs the planner with its resolver, run repository, and trigger repository. The planner implementation keeps those collaborators as constructor requirements; transaction-scoped catalog reads use the same resolver instance throughout a plan.

Batch owners pass identities already processed for the current entity as `excludedOncePerSubjectPolicies`, keyed by the run's stable `pluginId`/`hookSlug` and the batch's deterministic subject key. Before-event `once-per-subject` hooks are excluded before budget counting and insertion; participating request triggers retain the normalized exclusions.

A logical batch opens, records its changes and seals inside one transaction. Before its first write it resolves its applicable batch-hook candidates and pins their revisions and scripts in that transaction's memory. Only batches with candidates keep committed item change evidence. Sealing creates matching immutable batch triggers and runs before the transaction commits. A batch hook receives changed items belonging to its exact definition owner in its scope/resource chunk, even when only some match its local targets. Its pinned projection selects properties. Item hooks (`frequency` omitted or `"item"`) match only non-batch triggers and batch hooks match only batch triggers. `executionScope` is compared against the run's `executionUserId`, not the trigger's scope user.

`LifecyclePlanner.planBatch` groups committed evidence by scope user and chunks it in item order by both `AUTOMATIONS_BATCH_MAX_ITEMS` and the batch payload byte budget. It derives each chunk's trigger from the write identity and chunk index. Invocation preparation applies the pinned run projection and enforces the 64 KiB sandbox context limit. Callers dispatch item runs before batch runs. Prepared-persist APIs (`persistPreparedUpdate`, `persistPreparedUserCreate`, and their siblings) return item dispatch references only; the service owning a multi-item write seals one batch per resource.

Planning takes the per-plugin configuration lock in shared mode, because it only reads the pointers it pins; configuration writers take the same key exclusively. The root advisory budget lock applies when matching automation work is admitted, not for a no-hook write. The resolver caches locked catalogs within a transaction. The trigger repository persists a participating trigger's final decision once, before any recipients or runs, in the same transaction.

Retry policy belongs to the pinned after hook. Only classified infrastructure failures retry automatically, and external HTTP hooks require explicit run-ID idempotency. A workflow waiting on required hooks or a before-policy submits only runs that were never claimed, so replays do not resubmit, and awaits only runs it submitted or whose execution joined its workflow tree; a run another tree claimed is reported pending. It races their exits against one durable clock at its journaled absolute deadline, stops awaiting the losing clock, then records the outcome once from the attempt rows (finished before the deadline or not), so the outcome does not depend on which side woke it. Callers outside a workflow re-read the attempts every 50 ms until the deadline. The frequent reconciler claims due queued runs. Runs are queued at planning time, so a first attempt is reconciled only after the committing workflow has had its full wait to submit it. Before-policy failures never retry. Missing retained evidence, a missing or incompatible projection, non-JSON projected data, projected input over 64 KiB, and projected-schema failure all fail closed with bounded preparation diagnostics. Execution records remain internal; there is no history page, manual retry API, or RyotQL catalog access to them.

## Causation And Limits

Every trigger carries an initiator, source, execution ID, root execution ID, depth, optional parent trigger, and optional parent run. Automation host mutations derive this context from the trusted run; plugin input cannot choose its parents. Command request and committed change triggers retain their direct link, while both remain attributed to the parent run. The root budget blocks descendants beyond the configured depth or run count and records omitted hooks without executing them.

Notification subscriptions remain user configuration and select an exact plugin/kernel owner plus local signal slug. Formatter hooks resolve within that owner. A signal trigger snapshots its recipient set, then creates at most one run for each matching user/hook pair. Entity, event, relationship and provider-import evidence carries the stored schema owner; event matching also includes its parent entity schema. Provider-import completion uses the same trigger, run, attempt, causation, retry, and history model as domain mutations.

User-scoped after hooks may explicitly observe kernel collection `review`, `add-entity-to-collection`, and `remove-entity-from-collection` events with a kernel-owned target. Before policies remain local to their plugin, and global kernel observers are not allowed. Matching requires kernel event and parent ownership, not the name `collection`; a plugin may independently declare that same local name. Retained runs use their captured targets. Observation does not change the executing plugin's domain-write principal; kernel collection writes still require the existing explicit collection capability.

Retained triggers remain complete immutable evidence for participating hooks; projection narrows only the sandbox invocation. RyotQL exposes current state only and cannot reconstruct trigger-time evidence. Later updates, deletion, or plugin changes must not alter accepted execution input. Automation-history pruning can remove sensitive attempt detail and expired executable material without removing event write counts.

User-owned commands and sandbox subjects carry the exact user ID and a random database-owned account-generation token. Admission checks this token and account retirement under the account row lock on committing writes. Workflow executions record the account they work for at admission. Account reset closes admission and interrupts those executions before deleting its idempotency keys; recreating the same user ID issues a different token. User bootstrap and user-driven population execution IDs include the generation.
