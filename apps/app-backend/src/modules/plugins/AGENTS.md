# Plugins Module

- Plugin identity (`plugin.id`, scoped by `scope` + `slug` + `ownerId`) and installation identity (`plugin_installation.id`) are separate.
- System installations are provisioned by exactly two paths: user bootstrap, and the boot-ingestion backfill for all existing users. Both run one idempotent `on conflict do nothing` statement, so a default row is `health = 'ready'`, `is_disabled = false`, `sort_order = 0`, `config = {}`, and backup account-cleanliness treats exactly that shape as clean. Admin-gated `testSupport.installSystemPlugin` does not provision, so a system plugin ingested that way has no installation rows until the next boot.
- Because every provisioned row starts with `sort_order = 0`, system installations tie and resolve by slug until a user persists an explicit order.
- Trust is decided by the internal shipped-source ingestion path plus persisted `plugin.scope = 'system'`, never by a slug allowlist. `bootConfiguredPluginSlugs` survives only as the shipped-package uninstall fence.
- The process-wide `PluginLoader` snapshot holds system plugins only. Private plugins are never loaded into it, so private ingestion must not publish registry invalidation and must not replace the snapshot.
- Private ingestion compiles outside the ingestion mutation semaphore; only its persistence transaction takes the ingestion advisory lock.
- `validatePrivateManifestSurfaces` rejects every surface this slice cannot run for a private plugin. Later tasks shorten that list as they land user-scoped registries; `boot` stays rejected permanently.
- Private script, operation and config lookups read `plugin`/`plugin_installation` directly because the snapshot cannot answer them; system lookups keep resolving through the snapshot.
- `resolvePluginConfigContext` is a security boundary: a private plugin's config resolves only for its exact owner installation and must never fall back to `RYOT_PLUGIN_*` environment values. Ready/enabled checks belong at new dispatch and catalog boundaries so already-pinned work can finish after disablement.
- `ImportSourceCatalog` and `IntegrationProviderCatalog` are per-user and read `listPluginsAvailableToUser` once per call, so a source or provider and its script always resolve against one consistent view. Both `Live` layers use `Layer.provide`, not `Layer.provideMerge`: re-exporting `PluginRuntimeResolver` upward makes sibling layers in a `Layer.mergeAll` race and trips `TS377035`.
- Owned catalog lookups key on `plugin_installation.id`, never on a plugin slug or plugin id, so "same installation" is a literal identity comparison.
- Operation dispatch resolves through `findOperationAvailableToUser` in the effective registry of whoever the caller turns out to be. For `auth: "integration"`, the resolved operation's installation must equal the integration's installation; every authority failure returns the same `operation-not-found` so responses do not distinguish a missing operation from a foreign one.
- An `integrationId` is a bearer credential: presenting a valid enabled one executes with its owner's authority. It now unlocks only operations declared by its own installation.
- A non-`push` integration provider must reference a `script`-kind script, which `validatePrivateManifestSurfaces` still rejects, so private integration providers are `push`-only until a later task widens the private script-kind allowlist.
