# Plugins Module

- Plugin identity (`plugin.id`, scoped by `scope` + `slug` + `ownerId`) and installation identity (`plugin_installation.id`) are separate.
- System installations are provisioned by exactly two paths: user bootstrap, and the boot-ingestion backfill for all existing users. Both run one idempotent `on conflict do nothing` statement, so a provisioned row is `is_disabled = false`, `sort_order = 0`, `config = {}` and `health = 'ready'` from user bootstrap or `'installing'` from the boot backfill, and backup account-cleanliness treats exactly those two shapes as clean. Admin-gated `testSupport.installSystemPlugin` does not provision, so a system plugin ingested that way has no installation rows until the next boot.
- Because every provisioned row starts with `sort_order = 0`, system installations tie and resolve by slug until a user persists an explicit order.
- Trust is decided by the internal shipped-source ingestion path plus persisted `plugin.scope = 'system'`, never by a slug allowlist. `bootConfiguredPluginSlugs` survives only as the shipped-package uninstall fence.
- The process-wide `PluginLoader` snapshot holds system plugins only. Private plugins are never loaded into it, so private ingestion must not publish registry invalidation and must not replace the snapshot.
- Private ingestion compiles outside the ingestion mutation semaphore; only its persistence transaction takes the ingestion advisory lock.
- `validatePrivateManifestSurfaces` now rejects only `boot` (permanently: private code must never run with instance authority at startup) and `httpRateLimits` (instance-global policy with nowhere per-user to live yet). Every other surface, including `operations`, `crons`, `userBootstrap` and all `bindings.*` collections, is validated by `validatePluginManifestReferences` and `validatePluginExecutableScripts` like a system package.
- Private script, operation and config lookups read `plugin`/`plugin_installation` directly because the snapshot cannot answer them; system lookups keep resolving through the snapshot.
- `resolvePluginConfigContext` is a security boundary: a private plugin's config resolves only for its exact owner installation and must never fall back to `RYOT_PLUGIN_*` environment values. Ready/enabled checks belong at new dispatch and catalog boundaries so already-pinned work can finish after disablement.
- `ImportSourceCatalog` and `IntegrationProviderCatalog` are per-user and read `listPluginsAvailableToUser` once per call, so a source or provider and its script always resolve against one consistent view. Both `Live` layers use `Layer.provide`, not `Layer.provideMerge`: re-exporting `PluginRuntimeResolver` upward makes sibling layers in a `Layer.mergeAll` race and trips `TS377035`.
- Owned catalog lookups key on `plugin_installation.id`, never on a plugin slug or plugin id, so "same installation" is a literal identity comparison.
- Operation dispatch resolves through `findOperationAvailableToUser` in the effective registry of whoever the caller turns out to be. For `auth: "integration"`, the resolved operation's installation must equal the integration's installation; every authority failure returns the same `operation-not-found` so responses do not distinguish a missing operation from a foreign one.
- An `integrationId` is a bearer credential: presenting a valid enabled one executes with its owner's authority. It now unlocks only operations declared by its own installation.
- A non-`push` integration provider must reference a `script`-kind script. Private packages may now declare those scripts, so private integration providers are no longer `push`-only.
- `getEffectiveDefinitions` includes `installing` installations because a private installation's user-bootstrap entries run before it turns `ready` and must read their own plugin's schemas. Runtime availability (`availablePluginIdsForUser`, `listPluginsAvailableToUser`) stays strictly `ready` and enabled.
- Automation bindings are keyed on the stable `plugin.id`, never the plugin slug, and each binding carries the content hash it was built from, so a binding's script is resolved as `(pluginId, scriptSlug, contentHash)` instead of a global slug search. `listAutomations`, `findAutomation` and `listProviderEntityImportAutomations` therefore all take the data owner and enumerate that owner's effective registry; a `null` owner means a global row and falls back to the system snapshot.
- Private cron is discovered per ready, enabled installation and dispatched with owner authority under `privatePluginCronExecutionId`, a separate id space from the one-per-instance system `pluginCronExecutionId`. `resolvePrivatePluginCron` re-checks availability and the current content hash at dispatch time because discovery and dispatch are separate ticks.
- A private installation is persisted `installing` and becomes `ready` only through `PluginInstallationWorkflow`. The service dispatches that workflow after its persistence transaction commits, never inside it, and marks the installation `failed` when the dispatch itself cannot be enqueued.
- `PluginInstallationService` must never gain a hard `WorkflowEngine` requirement: it is also built into `MigrationInfrastructureLive`. `PluginInstallationLifecycleDispatcher` defaults to a no-op for migration and shipped-system ingestion, and `layers.ts` provides the live dispatcher only on the runtime path. That runtime variant must wrap `Layer.fresh(PluginInstallationService.layer)`: both variants share one layer object, layers memoize by object identity, and the migration build runs first, so without it the runtime silently inherits the no-op dispatcher and every private installation stays `installing` forever.
- Bootstrap entries are executed from the workflow body, never from an Activity, because `SandboxExecutionService.executeScript` starts `SandboxScriptWorkflow`. Their execution ids derive from installation id plus entry slug, so replay reuses the same durable execution instead of repeating the effect.
- `begin-plugin-installation` returns null unless the installation still exists and is `installing`. That is what makes a duplicate dispatch a no-op and why a package update can never re-run bootstrap.
- Persisted bootstrap failure reasons are built in the workflow body from the entry slug alone; sandbox messages are logged, never stored on the installation.
- A shipped package is authoritative over a private one. `reconcileSystemInstallations` marks a colliding private installation `incompatible` with a truncated diagnostic, but only from `ready` or `incompatible`: an `installing` row is owned by its in-flight lifecycle workflow, and flipping it out of `installing` would make that workflow's `begin` a permanent no-op and strand the installation without its `userBootstrap` entries, so it is left to reach `ready` and be re-detected at the next boot. It removes that installation's generated views whatever its health, including `installing`, and re-materializes the owner's definitions once per owner whenever any of that owner's rows changed health in either direction, because a shipped release can claim a saved view slug the private row still holds and a stale row makes `ensureBuiltinViews` fail.
- Conflict detection evaluates each private plugin against the shipped set alone, never through `buildEffectiveDefinitions`, because a private plugin may legitimately reference a sibling private plugin's definitions and a whole-set compose would misattribute blame.
- `getEffectiveDefinitions` drops private definitions in one ordered pass (entity schemas, then relationship schemas, then signal schemas and saved views) so that both a slug the base source already claims and a structural reference to a dropped sibling definition are filtered out, never left to throw inside `buildDefinitionSnapshot`. Everything non-colliding still composes under its qualified `pluginId`.
- `provisionSystemInstallationsForAllUsers` inserts `installing` rows for bootstrap-completed users only, and that row is the durable work record the runtime `PluginInstallationSweepDispatcherLive` re-dispatches; `provisionSystemInstallationsForUser` inserts `ready` because `performBootstrap` runs the entries inline right after. The sweep lives in its own module because `installation-service` already imports `installation-workflow`.
- `getEffectiveDefinitions(userId, true)` means "also include disabled and still-`installing` installations", never `incompatible` ones: a conflicted installation must not reach any composed view, including the `ensureBuiltinViews` and signal-schema resolution paths that pass the flag, or reconcile would delete its rows and the next materialize would recreate them.
- `PluginInstallationWorkflow` serves both scopes, so `begin` gates on `installing` health alone, and `complete` materializes the owner's plugin-declared saved views before turning the installation `ready`.
- Uninstall resolves the user's private plugin before the system snapshot, so a private installation shadowed by a newly shipped slug stays removable; only a slug with no private plugin returns the `system-plugin` conflict.
