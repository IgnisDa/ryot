# S3 — Scheduling and fairness

- **Outcome:** interactive and background lanes, with per-user and per-plugin fairness for sandbox
  executions and deployment-wide HTTP admission.
- **Status:** trusted lane classification and propagation, memory admission
  ([s3-memory.md](s3-memory.md)), durable fair selection, sidecar CPU admission and fair HTTP tickets
  are implemented, and tenant fairness passes on the reference host. The original latency criterion
  (loaded p95 within 10% of unloaded) fails on that host and is replaced by **E2**: pooled loaded p95
  ≤ 1.25× unloaded for search and ≤ 1.60× for details, with interactive and background work in separate
  backend processes and the background process at low CPU priority. Lane-pinned processes and the
  `SERVER_LANES=split` supervisor and provider request reductions are implemented. The six-pair
  measurement at `448dbda769` fails both E2 endpoint limits (see Results).
- **Prerequisites:** S1 and S2.
- **Scope:** trusted scheduling identity, durable execution admission, sidecar lane routing and CPU
  admission, Redis HTTP scheduling, lane-pinned backend processes, scheduling metrics, and fresh-host
  acceptance measurements.
- **Non-goals:** S4 image verification and deployment requirements, S5 live HTTP settlement,
  S6 V8 changes, import fan-out reduction, and multi-host deployment.

## Memory admission

The approved memory contract, including the per-run reservation, lane transient pools, lazy
journal, admission modes and canonical budget, is [s3-memory.md](s3-memory.md). Scheduling below must
respect its admission predicate and lock order.

## Scheduling identity and classification

- The human executing user is the tenant: `subject.userId` for user subjects and
  `subject.executionUserId` for automation subjects. User-less system work shares one capped system
  tenant. First-party work for a user charges that user, regardless of its system trust tier.
- The plugin key is the pinned plugin ID, not its revision, script, provider, slug, or content hash.
  Kernel work has a bounded kernel bucket within its tenant. Adding plugins cannot increase a user's
  share. Trust routing and crash-quarantine owner/content keys retain their separate meanings.
- The trusted initiating backend path selects the lane. User-facing provider search, resolution,
  details, and awaited operations use `interactive`; imports, scheduled integrations, detached
  jobs, and async after-hook automation use `background`. Before-policy work, required after-hooks
  and awaited children inherit their initiating lane. Import-driven provider details remain background.
- Persist the lane with the workflow and durable queue payload. Propagate it through child workflows,
  replays, host dispatch, recovery, and backend restart. Never infer it solely from script kind or
  accept a priority from script context, archive metadata, or a host-call argument.
- Inventory all initiating call sites and test classification before changing runtime admission.
  Missing classification fails at the trusted boundary; there is no implicit interactive default.

## Execution admission

- Keep `SANDBOX_WORKER_CONCURRENCY` as one global bound across trust tiers, snapshot tiers, shards,
  grants, parked executions, and recovery. Preserve database headroom and memory ceilings.
- Admit interactive work first while reserving background progress. Within a lane, select tenants
  round-robin; within a tenant, select plugins round-robin; within a plugin, preserve FIFO order.
  Interactive work may use any free slot; background work is capped at its share of the slots and
  goes first after four consecutive interactive admissions while it is ready and has none in flight.
- On the canonical host with global concurrency two, admit at most one background execution at a
  time and keep the second run's required resources available to interactive work. An execution
  already running is not cancelled merely because a higher-priority request arrives.
- Perform fair selection before durable workers are occupied by a tenant's backlog. The existing
  durable queue remains the work owner; a fair semaphore behind its FIFO worker is insufficient.
  Do not create a second background job system or decode journals before reservation.
- Ephemeral waiters remain bounded. Background backlog cannot consume every interactive waiter
  position. Cancellation removes tickets and releases counters exactly once; retries cannot jump
  ahead by creating a new identity. Fairness state is bounded and idle identities expire.
- Memory, process-start, recovery, and database waits must not hold resources in an order that
  blocks an otherwise admissible interactive request. Exclusive crash probes retain S2 attribution
  semantics and do not bypass global bounds.

## Sidecar CPU admission

- Send the selected lane in both backend lease entry and the Rust run frame. Recovery preserves it.
  Use the existing separate lane worker pools and lower background thread priority.
- CPU-slot admission and reacquisition after host waits prioritize interactive work and preserve
  background progress. Apply the policy to initial polling and synchronous inline resumption.
- Preserve the CPU-active cap, platform-thread cap, cancellation wakeup, script-time accounting,
  termination grace, and process backstop. CPU limits are not fair-scheduling time slices.
- Scheduling is global across processes in its resource bounds. Independent sidecar CPU queues
  cannot multiply background admission across snapshot or trust tiers.

## Global HTTP admission

- Preserve deployment-wide policy resolution, Redis time, declaration hashes, no-burst spacing,
  `Retry-After` blocks, confirmation before network dispatch, durable retry, and fail-closed errors.
- Replace arrival-ordered future slot reservations with bounded, execution-bound pending tickets.
  Select ready tickets by lane, tenant, and plugin using the execution policy above. A tenant cannot
  monopolize future slots by reserving a long backlog or rotating plugins.
- Selection and slot consumption are atomic across backend instances. A ticket has a trusted,
  stable logical request identity; duplicate registration, workflow replay, or confirmation cannot
  consume another slot or repeat network work already committed by its activity.
- Admission waits hold no isolate or worker: matched HTTP calls continue to defer out of the live
  isolate, and each hop's admission waits in memory inside one activity, so waits add no journal
  entries or workflow replays. S3 does not introduce S5 short-wait settlement.
- Cancelled or abandoned tickets expire within a bounded lease; inactive tenants cannot block the
  head of a queue indefinitely. Stale policy declarations invalidate their tickets. Policy changes
  preserve existing provider blocks, and backend restart cannot reset the global schedule.
- Keep Redis keys, schemas, parsing, and atomic scripts in Redis infrastructure. Bound pending
  tickets and cleanup work per command; overload stays pending without allocating an
  unbounded Redis or backend queue. Unmatched requests retain existing network policy.

## Process separation

- `SERVER_LANES` selects the public topology: `all` (default, one process, no runner listener) or
  `split` (a supervisor with interactive and background role children). Split roles share one Postgres
  and Redis.
- The interactive role serves HTTP and runs interactive-lane sandbox work and workflows; the background
  role runs everything else, including schedulers and lane-less workflows. Each role owns its sidecars,
  memory budget and database pool.
- Workflows that run on interactive request paths have an interactive definition in their own shard
  group; the lane is part of the workflow name because execution IDs are hashed. Unknown or lane-less
  work maps to the background role.
- The supervisor creates a private mode-0700 temporary directory for role sockets (mode 0600), passes
  it to both children as private `RYOT_RUNNER_SOCKET_DIR`, and removes it after both roles stop. Each
  child uses private `RYOT_SERVER_ROLE` to select its role and `SERVER_LANES=all`; operators do not
  configure the socket directory or launch role processes directly. Roles exchange cluster messages
  over Unix sockets with pinned NDJSON framing (16 MiB per frame), the same JSON codec message storage
  uses; the runner never listens on TCP.
- Clients never choose a lane. The server derives it from the initiating path.
- `SERVER_LANES=split` makes the entry point a supervisor: it runs a migration-only child first
  (`RUN_MIGRATION_ONLY=true`, `SERVER_LANES=all`) and aborts if it fails, then starts the `interactive`
  and `background` roles from the same entry point with `SERVER_LANES=all` and private role settings.
  The background role runs under `nice -n 19`, so its sidecars inherit the priority. Scoped Effect child
  resources are finalized in parallel. When either role exits, the supervisor terminates the other and
  exits with the first exit code; on SIGTERM or SIGINT it sends SIGTERM to both roles and allows 30
  seconds for graceful termination before SIGKILL.
- In `split`, `SANDBOX_MEMORY_BUDGET_MIB` is the deployment total (half the effective memory when
  unset) and each role receives half. A half below the shared-mode minimum of 854 MiB, a total below
  1,708 MiB, fails supervisor start. A process serving one lane gives it the whole worker capacity and
  plans one shared memory pool; the background cap of half the workers and lane-mode pools apply only
  to a process serving both lanes. `DATABASE_POOL_MAX` and `SANDBOX_WORKER_CONCURRENCY` apply per role.
- Each role writes its own structured log (`<stem>.<role><ext>` beside `SERVER_LOG_FILE`; god-mode
  server logs list all of them) and exports OTLP metrics with the resource attribute
  `ryot.server.role`, so each role has its own cumulative series.

## Provider request cost and result delivery

- HTTP policy resolution and durable admission share one activity. The activity persists its cleanup
  policy so interrupted replay and cancellation retain the original ticket binding after policy changes.
- Mutation ownership and retirement checks share one query after the account share lock, retaining a
  fresh post-lock snapshot. Workflow admission shares the execution-root fence; replies and garbage
  collection retain exclusive access.
- Plugin revisions store a compact generated sandbox-authority projection. Every invocation still
  checks live ownership, activation and configuration; invalid authority fails schema decoding.
- Each backend role caches verified compiled modules by content hash, with at most 16 entries and
  1 MiB per module. Cache failures are not retained, and every invocation reserves fresh authority.
- Provider population reads only entity identity, ownership and the required relationships. PostgreSQL
  effective definitions remain authoritative; no Redis definition projection is needed.
- Import result requests long-poll for at most 20 seconds. Scoped local and Redis notifications wake
  readers after committed terminal changes, admission or cancellation; reconnect also wakes readers.
  The client counts a monotonic 120-second running budget, excluding queued observations.
- Root `WorkflowEngine.execute` completion delivery remains deferred to
  [Effect #9003](https://github.com/Effect-TS/effect/issues/9003). The adoption TODO remains in
  `kernel/backend/src/modules/mutations/workflow-dispatch.ts`.

## Benchmark protocol

- Use the provided 2 vCPU / 4 GB x86_64 host; record actual memory, CPU model, kernel, effective
  cgroup limits, revision, configuration, and running services. Prepare fresh equivalent DB/Redis
  state for each trial. Pin provider responses and business inputs.
- The harness starts the server with `SERVER_LANES=split` in both unloaded and loaded trials, with
  `SANDBOX_MEMORY_BUDGET_MIB=1904` (the deployment total, 952 MiB per
  role), `SANDBOX_WORKER_CONCURRENCY=2` and `DATABASE_POOL_MAX=10` per role. The CPU and RSS samplers
  walk the supervisor's process tree.
- The metrics sink keeps one snapshot stream per `ryot.server.role` and drops the migration process's
  `all` stream. Trial records store `metrics` per role; the summarizer takes deltas per role and sums
  them, requires at least two snapshots from every role present, and reads background-lane dispatches
  for the stall check from the `background` stream (`all` in single-process records). Admission timings
  come from every role's log, so samples keep their ticket wait and resume delay.
- E2 limits are applied per endpoint to pooled p95: search at most 1.25 and details at most 1.60 of
  unloaded. The summary reports the topology next to the verdict.
- Run a warmed unloaded trial and a matched loaded trial, interleaved over at least five pairs.
  Measure complete authenticated search and details requests, including workflow, queue, HTTP,
  database, and sidecar time. Report loaded and unloaded p50 and p95, sample counts, and raw timings.
  Acceptance pools p95 over six pairs of 20 warm-up and 200 measured requests per endpoint.
- Keep background imports continuously ready, demonstrate CPU saturation, and record import
  progress. A workload that fails to saturate CPU or stops background work does not prove latency
  isolation. Report replay/admission counts, CPU, aggregate RSS, memory reservations, queue waits,
  database occupancy, HTTP ticket waits, and lane dispatches.
- For tenant fairness, use equal-cost continuously ready work for two users, with multiple plugins
  saturating one user. Require each user to receive half of execution dispatches and matched HTTP
  admissions, within one completed scheduling round after initial in-flight work. Test system-plugin
  work on behalf of users as well as uploaded plugins. Report latency and progress for both users.
- Run benchmark orchestration under a `ryot-s3-benchmark` systemd service, with persisted logs and
  results. Reconnect to observe the unit; SSH lifetime must not own the benchmark process. Validate
  build, preparation, reset, and measurement exit codes before accepting results.

## Stops

Stop and report if trusted lane propagation or fair selection needs a wider workflow redesign;
if the canonical topology cannot retain interactive memory headroom under existing legal limits;
if fair HTTP tickets cannot remain atomic, bounded, replay-safe, and fail-closed; or if real
background saturation violates E2. Do not weaken acceptance or retune unrelated database pools to
obtain a pass. Record every unproved item and deviation before requesting a decision.

### Separation bounds

Separate interactive and background stacks on the same host bound what process separation can reach.
The background stack ran the loaded workload at CPU weight 1 and the interactive stack the unloaded
trial at weight 10,000, 40 measured requests per endpoint (ms):

| Setup                                               | Search p95 | Ratio | Details p95 | Ratio |
| --------------------------------------------------- | ---------- | ----- | ----------- | ----- |
| Fully separate stacks, including Postgres and Redis | 700        | 1.16  | 6,560       | 1.54  |
| Same, background stack frozen                       | 600        | 0.99  | 4,267       | 1.00  |
| Shared Postgres and Redis, 1 s hook poll            | 641        | 1.08  | 7,554       | 1.80  |
| Shared Postgres and Redis, 100 ms hook poll         | 676        | 1.17  | 5,206       | 1.30  |

The frozen run matches the unloaded baseline, so memory pressure does not explain the gap, and even
full separation leaves details at 1.54×, so the 10% criterion is not reachable on this 2 vCPU host. With
shared infrastructure, details misses E2 only while required hooks are observed by a 1 s poll; with a
prompt wake-up both endpoints meet E2, CPU stays at 97.7% busy and background dispatches advance in
every 10 s interval. The durable hook wait above provides that wake-up without polling.
