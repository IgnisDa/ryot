# S3 — Scheduling and fairness

- **Outcome:** interactive and background lanes, with per-user and per-plugin fairness for sandbox
  executions and deployment-wide HTTP admission.
- **Status:** prefix inspection, atomic resource admission, trusted lane classification and
  propagation, and lane-mode memory admission ([s3-memory.md](s3-memory.md)) are implemented. The remaining scheduling contract requires approval before
  implementation.
- **Prerequisites:** S1 and S2, approval of this contract, and the memory admission in
  [s3-memory.md](s3-memory.md).
- **Scope:** trusted scheduling identity, durable execution admission, sidecar lane routing and CPU
  admission, Redis HTTP scheduling, scheduling metrics, and fresh-host acceptance measurements.
- **Non-goals:** S4 deployment sizing, S5 live HTTP settlement, S6 V8 changes, and import fan-out
  reduction.

## Decisions requiring approval

Approve the durable selection mechanism, lane allocation and borrowing policy, HTTP ticket
lifecycle, and benchmark statistics separately.

## Memory admission

The approved memory contract, including the per-run reservation, lane transient pools, lazy
journal, admission modes and canonical budget, is [s3-memory.md](s3-memory.md). Scheduling below must
respect its admission predicate and lock order.

## Scheduling identity and classification

- The human executing user is the tenant: `subject.userId` for user subjects and
  `subject.executionUserId` for automation subjects. User-less system work shares one capped system
  tenant. First-party work for a user charges that user, regardless of its system trust tier.
- The plugin key is the pinned plugin ID, not its revision, script, provider, slug, or content hash.
  Kernel work has a bounded kernel bucket within its tenant. Adding plugins cannot increase a user's
  share. Trust routing and crash-quarantine owner/content keys retain their separate meanings.
- The trusted initiating backend path selects the lane. User-facing provider search, resolution,
  details, and awaited operations use `interactive`; imports, scheduled integrations, detached
  jobs, and async after-hook automation use `background`. Before-policy work, required after-hooks
  and awaited children inherit their initiating lane. Import-driven provider details remain background.
- Persist the lane with the workflow and durable queue payload. Propagate it through child workflows,
  replays, host dispatch, recovery, and backend restart. Never infer it solely from script kind or
  accept a priority from script context, archive metadata, or a host-call argument.
- Inventory all initiating call sites and test classification before changing runtime admission.
  Missing classification fails at the trusted boundary; there is no implicit interactive default.

## Execution admission

- Keep `SANDBOX_WORKER_CONCURRENCY` as one global bound across trust tiers, snapshot tiers, shards,
  grants, parked executions, and recovery. Preserve database headroom and memory ceilings.
- Admit interactive work first while reserving background progress. Within a lane, select tenants
  round-robin; within a tenant, select plugins round-robin; within a plugin, preserve FIFO order.
  The background share and whether unused interactive capacity may be borrowed require approval.
- On the canonical host with global concurrency two, admit at most one background execution at a
  time and keep the second run's required resources available to interactive work. An execution
  already running is not cancelled merely because a higher-priority request arrives.
- Perform fair selection before durable workers are occupied by a tenant's backlog. The existing
  durable queue remains the work owner; a fair semaphore behind its FIFO worker is insufficient.
  Do not create a second background job system or decode journals before reservation.
- Ephemeral waiters remain bounded. Background backlog cannot consume every interactive waiter
  position. Cancellation removes tickets and releases counters exactly once; retries cannot jump
  ahead by creating a new identity. Fairness state is bounded and idle identities expire.
- Memory, process-start, recovery, and database waits must not hold resources in an order that
  blocks an otherwise admissible interactive request. Exclusive crash probes retain S2 attribution
  semantics and do not bypass global bounds.

## Sidecar CPU admission

- Send the selected lane in both backend lease entry and the Rust run frame. Recovery preserves it.
  Use the existing separate lane worker pools and lower background thread priority.
- CPU-slot admission and reacquisition after host waits prioritize interactive work and preserve
  background progress. Apply the policy to initial polling and synchronous inline resumption.
- Preserve the CPU-active cap, platform-thread cap, cancellation wakeup, script-time accounting,
  termination grace, and process backstop. CPU limits are not fair-scheduling time slices.
- Scheduling is global across processes in its resource bounds. Independent sidecar CPU queues
  cannot multiply background admission across snapshot or trust tiers.

## Global HTTP admission

- Preserve deployment-wide policy resolution, Redis time, declaration hashes, no-burst spacing,
  `Retry-After` blocks, confirmation before network dispatch, durable retry, and fail-closed errors.
- Replace arrival-ordered future slot reservations with bounded, execution-bound pending tickets.
  Select ready tickets by lane, tenant, and plugin using the execution policy above. A tenant cannot
  monopolize future slots by reserving a long backlog or rotating plugins.
- Selection and slot consumption are atomic across backend instances. A ticket has a trusted,
  stable logical request identity; duplicate registration, workflow replay, or confirmation cannot
  consume another slot or repeat network work already committed by its activity.
- Durable waits release execution resources. Matched HTTP calls continue to defer out of the live
  isolate; S3 does not introduce S5 short-wait settlement.
- Cancelled or abandoned tickets expire within a bounded lease; inactive tenants cannot block the
  head of a queue indefinitely. Stale policy declarations invalidate their tickets. Policy changes
  preserve existing provider blocks, and backend restart cannot reset the global schedule.
- Keep Redis keys, schemas, parsing, and atomic scripts in Redis infrastructure. Bound pending
  tickets and cleanup work per command; overload stays durably pending without allocating an
  unbounded Redis or backend queue. Unmatched requests retain existing network policy.

## Benchmark protocol

- Use the provided 2 vCPU / 4 GB x86_64 host; record actual memory, CPU model, kernel, effective
  cgroup limits, revision, configuration, and running services. Prepare fresh equivalent DB/Redis
  state for each trial. Pin provider responses and business inputs.
- Run a warmed unloaded trial and a matched loaded trial, interleaved over at least five pairs.
  Measure complete authenticated search and details requests, including workflow, queue, HTTP,
  database, and sidecar time. Report loaded and unloaded p50 and p95, sample counts, and raw timings.
  The acceptance percentile and trial count require approval; the plan's 10% threshold is fixed.
- Keep background imports continuously ready, demonstrate CPU saturation, and record import
  progress. A workload that fails to saturate CPU or stops background work does not prove latency
  isolation. Report replay/admission counts, CPU, aggregate RSS, memory reservations, queue waits,
  database occupancy, HTTP ticket waits, and lane dispatches.
- For tenant fairness, use equal-cost continuously ready work for two users, with multiple plugins
  saturating one user. Require each user to receive half of execution dispatches and matched HTTP
  admissions, within one completed scheduling round after initial in-flight work. Test system-plugin
  work on behalf of users as well as uploaded plugins. Report latency and progress for both users.
- Run benchmark orchestration under a `ryot-s3-benchmark` systemd service, with persisted logs and
  results. Reconnect to observe the unit; SSH lifetime must not own the benchmark process. Validate
  build, preparation, reset, and measurement exit codes before accepting results.

## Stops

Stop and report if trusted lane propagation or fair selection needs a wider workflow redesign;
if the canonical topology cannot retain interactive memory headroom under existing legal limits;
if fair HTTP tickets cannot remain atomic, bounded, replay-safe, and fail-closed; or if real
background saturation violates the latency threshold. Do not weaken acceptance or retune unrelated
database pools to obtain a pass. Record every unproved item and deviation before requesting a decision.

## Results

The real-saturation latency criterion fails, which is a stop condition. All deterministic acceptance
tests pass with `bun run check` and `bun turbo --filter='!@ryot-app/e2e' test`; CI has not run.
The reference host is AMD EPYC-Genoa, 2 vCPU, 3.7 GiB RAM, no swap, Linux 7.0.0 x86_64, running the
`ryot-s3-benchmark` unit with `S3_BENCHMARK_CPU_ITERATIONS=1200000` and
`S3_BENCHMARK_BACKGROUND_GATES=2`. `scripts/s3-benchmark.sh` runs each trial against fresh
containers and a fresh server, and `scripts/s3-summarize.ts` validates and pools the records.

Interactive latency, one matched pair of 200 measured requests each after 20 warm-ups (ms):

| Endpoint | Unloaded p50 | Unloaded p95 | Loaded p50 | Loaded p95 | p95 ratio | Limit |
| -------- | ------------ | ------------ | ---------- | ---------- | --------- | ----- |
| search   | 570.5        | 596.1        | 1,309.7    | 1,945.6    | 3.26      | 1.10  |
| details  | 4,161.7      | 4,294.6      | 13,903.1   | 16,537.1   | 3.85      | 1.10  |

- The loaded trial held CPU at 93.5% mean busy (minimum 10 s rolling 89.8%) for 48.8 minutes.
  Background dispatches advanced in every 10 s metric interval, and two 1,001-item import gates
  completed. The summarizer judged this record invalid under the earlier stall check, which counted
  only outbound provider HTTP and saw a 798 s stall while imports persisted; the record is evaluated
  under the dispatch-based check now in the harness.
- HTTP ticket wait plus resume delay grew by 387 ms (search) and 212 ms (details) at the tail,
  against p95 increases of 1,350 ms and 12,243 ms; most of the increase lies outside HTTP admission.
- One pair ran instead of the approved six. With both ratios about 3x the limit, further pairs are
  not expected to change the outcome.

Tenant fairness, one trial with a 180 s window opened after both users' initial batches drained:

| User | Plugins                 | Executions in window | HTTP admissions in window | Failures |
| ---- | ----------------------- | -------------------- | ------------------------- | -------- |
| a    | 3 uploaded and 1 system | 17                   | 17                        | 0        |
| b    | 1 uploaded              | 17                   | 18                        | 0        |

Executions differ by 0 (tolerance 4) and admissions by 1 (tolerance 2), so the fairness criterion
passes for that trial.

### Where loaded details time goes

`scripts/s3-benchmark.sh` persists server traces next to each record. Each measured details request is
split at 1 ms resolution into sandbox queue wait and sandbox processing for its own interactive steps
and automation hooks, SQL time outside those, and the remainder. Means over 40 requests per mode (ms):

| Component           | Unloaded | Loaded | A1 unloaded | A1 loaded |
| ------------------- | -------- | ------ | ----------- | --------- |
| interactive queue   | 3        | 4      | 3           | 4         |
| interactive process | 132      | 393    | 121         | 327       |
| hook queue          | 14       | 2,328  | 19          | 421       |
| hook process        | 697      | 1,439  | 861         | 1,970     |
| database            | 1,793    | 6,332  | 1,888       | 7,237     |
| other               | 1,501    | 4,479  | 1,308       | 4,538     |
| total               | 4,140    | 14,976 | 4,199       | 14,497    |

Each details request runs two interactive provider steps and four automation hooks, all inside the

### Separation upper bound

Two independent stacks (backend, sidecar, Postgres, Redis each) on the same host bound what process
separation and CPU priority could reach. The background stack ran the loaded workload under
`CPUWeight=1` and Docker CPU weight 1, and the interactive stack ran the unloaded trial under weight
10,000, 40 measured requests each:

| Run                               | Search p95 | Details p95 | Ratio to unloaded |
| --------------------------------- | ---------- | ----------- | ----------------- |
| Interactive stack beside the load | 700        | 6,560       | 1.16 / 1.54       |
| Same, background stack frozen     | 600        | 4,267       | 0.99 / 1.00       |

With the background frozen, latency matches the unloaded baseline, so memory pressure does not explain
the gap. Even complete separation of every process, including the database, leaves details at 1.54×
on this 2 vCPU host in one 40-request trial, so the 1.10 criterion is not expected to be reachable
here by CPU scheduling alone.

### Required after-hooks in the waiting lane (A1)

Required after-hooks and the lifecycle work they cause now run in the lane of the command that waits
for them; async after-hooks stay background. One traced pair, 40 measured requests each (ms):

| Run       | Search p95 unloaded / loaded | Ratio | Details p95 unloaded / loaded | Ratio |
| --------- | ---------------------------- | ----- | ----------------------------- | ----- |
| Before A1 | 604 / 1,956                  | 3.24  | 4,268 / 16,847                | 3.95  |
| A1        | 585 / 2,271                  | 3.88  | 5,102 / 15,859                | 3.11  |

- Hook queue wait under load falls from 2,328 ms to 421 ms per details request, but loaded details
  mean improves only 3%: hook processing and SQL grow by 531 ms and 905 ms, offsetting 75% of the
  1,907 ms queue reduction.
- Interactive hooks lose inline settlement: in lane mode the interactive transient pool is smaller
  than an inline batch, so each of the three hooks that call `executeRyotql` takes an extra replay: the
  same four hooks take 11 sandbox runs per request instead of 8, and automation pending replays rise from 547 to 1,096
  for the same 180 completions.
- Search p95 under load rises from 1,956 to 2,271 ms, likely because hooks now share the interactive
  lane with it.
- The unloaded details p95 rises from 4,268 to 5,102 ms while its mean moves from 4,140 to 4,199 ms;
  with one 40-request trial per mode the tail is not separable from noise.

Durable wake-up for required hooks (replacing the 1 s in-workflow poll) is not built. The engine resumes
a parent from the child run's exit before the child's reply is saved, so a woken parent can read a stale
result; the design needs to await the saved child reply or re-check durably, classify every completion
path against the journaled deadline, decide `executePolicy` explicitly, and be tested under
`ClusterWorkflowEngine` rather than the in-memory engine.

### Separation with shared Postgres and Redis

The upper-bound stacks were rerun on one Postgres server and one Redis server (separate databases and
Redis logical databases), with backend and sidecar processes weighted as before and Postgres and Redis at
default weight. One session, 40 measured requests per endpoint per variant (ms):

| Variant                             | Search p95 | Ratio | Details p95 | Ratio | CPU busy | Background dispatches |
| ----------------------------------- | ---------- | ----- | ----------- | ----- | -------- | --------------------- |
| Interactive stack alone             | 596        | 1.00  | 4,205       | 1.00  | 64%      | —                     |
| Beside the load, background pool 10 | 641        | 1.08  | 7,554       | 1.80  | 96.9%    | 145.5 per minute      |
| Beside the load, background pool 7  | 682        | 1.14  | 7,644       | 1.82  | 96.9%    | 141.5 per minute      |

Background dispatches advanced in every 10 s metric interval in both loaded variants. Search meets E2;
details does not, so process separation alone cannot meet E2 with a shared database on this host, and
lowering the background pool does not help.

Loaded details latencies fall into clusters about 1 s apart (around 5.3, 6.4 and 7.5 s; unloaded
requests sit at 4.0 to 4.3 s). Across the clusters SQL time (2.6 to 2.8 s) and hook processing (about
1.0 s) stay level while the unattributed remainder steps from 1.6 to 2.6 to 3.5 s, matching the 1 s
in-workflow poll that observes required hooks. The fastest cluster is 1.27× the unloaded p95.

With the hook poll shortened to 100 ms in the same setup (one session, 40 measured requests each):

| Variant                             | Search p95 | Ratio | Details p95 | Ratio | CPU busy | Background dispatches |
| ----------------------------------- | ---------- | ----- | ----------- | ----- | -------- | --------------------- |
| Interactive stack alone             | 578        | 1.00  | 4,006       | 1.00  | 68%      | —                     |
| Beside the load, background pool 10 | 676        | 1.17  | 5,206       | 1.30  | 97.7%    | 111.5 per minute      |

### Event-driven required-hook wake-up (G1)

Required hooks and before-policies are now observed by a short-lived workflow that races the run against
a durable deadline. Traced single-process pair, same harness as the earlier traced runs (40 measured
requests per endpoint, ms):

| Build      | Search p95 unloaded → loaded | Ratio | Details p95 unloaded → loaded | Ratio | Loaded details mean |
| ---------- | ---------------------------- | ----- | ----------------------------- | ----- | ------------------- |
| Before A1  | 604 → 1,956                  | 3.24  | 4,268 → 16,847                | 3.95  | 14,976              |
| A1         | 585 → 2,271                  | 3.88  | 5,102 → 15,859                | 3.11  | 14,497              |
| A1 with G1 | 609 → 2,628                  | 4.32  | 4,408 → 18,696                | 4.24  | 17,028              |

Details latencies no longer cluster on whole seconds: before G1, 37 and 40 of 40 unloaded requests ended in the
first 300 ms of a second; with G1 they spread across the second. The unattributed remainder of unloaded
details falls from 1.3 to 0.75 s, but SQL time rises from 1.9 to 2.3 s unloaded and from 7.2 to 9.8 s
loaded, so unloaded details is unchanged and loaded details is slower on one process. Each request
starts three observer workflows; their workflow registration and garbage-collection bookkeeping adds
about 80 transactions and 210 statements per request (418 against 340 transactions).

### Parent-owned required-hook wait (G1b)

The waiting workflow races its own hook runs against one durable clock per call and no longer
resubmits runs on replay. Traced single-process pair, same harness (ms; SQL per details request):

| Build      | Search p95 unloaded → loaded | Ratio | Details p95 unloaded → loaded | Ratio | Loaded details mean | Transactions | Statements |
| ---------- | ---------------------------- | ----- | ----------------------------- | ----- | ------------------- | ------------ | ---------- |
| A1         | 585 → 2,271                  | 3.88  | 5,102 → 15,859                | 3.11  | 14,497              | 340          | 1,479      |
| A1 with G1 | 609 → 2,628                  | 4.32  | 4,408 → 18,696                | 4.24  | 17,028              | 418          | 1,712      |
| G1b        | 589 → 2,395                  | 4.07  | 4,153 → 16,665                | 4.01  | 15,605              | 386          | 1,603      |

G1b removes 33 of the 79 transactions G1 added and has the lowest unloaded details p95 measured, with
latencies spread over a narrow 3.8 to 4.2 s range rather than whole-second clusters. It does not reach
the A1 SQL level. The remainder against A1 is workflow messaging for the durable wait: about 34 more
admitted envelopes and 14 more replies per request, each carrying workflow garbage-collection
bookkeeping (find, root lock, admit or reply preparation), from the race's child executes and clock
schedules repeated on parent replays, the race and settle records, and the replays' journal reads.
