# Concept inventory

Each kernel concept, the feature it serves, and whether it stays. Verdicts follow the ground rules in
[`README.md`](README.md). Counts are from `ultra-rewrite` at `6b6ece2737`, non-test kernel backend code.

## Durable workflows

Of 33 workflow definitions, 11 are deleted, 15 become rows in one job table, and the remaining 7 merge into
2 durable workflows. The deleted ones all sit on the request path, which rule 4 makes a single transaction.

| Workflow                                                                                                                                               | What it does now                                               | Verdict | Becomes                                                                 |
| ------------------------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------- | ------- | ----------------------------------------------------------------------- |
| `EventCreateWorkflow`                                                                                                                                  | Event creates that miss the direct path or outlive 35 s        | Delete  | The direct transaction; large batches go through imports                |
| `PolicyBatchWorkflow`                                                                                                                                  | Runs before-policies for a batch                               | Delete  | A direct sandbox call before the commit                                 |
| `UserCommandWorkflow`                                                                                                                                  | A script's `commitUserChanges`                                 | Delete  | A function call and one transaction                                     |
| `UserEntityPreparationWorkflow`                                                                                                                        | Child of a user command                                        | Delete  | Part of that transaction                                                |
| `UserRelationshipPreparationWorkflow`                                                                                                                  | Child of a user command                                        | Delete  | Part of that transaction                                                |
| `CollectionMembershipWorkflow`                                                                                                                         | Adds or removes an item from a collection                      | Delete  | One transaction                                                         |
| `SandboxDurableHostServiceWorkflow`                                                                                                                    | One workflow per script host call                              | Delete  | The host call runs inline and appends to the execution's journal        |
| `UserBootstrapWorkflow`                                                                                                                                | Signup entities                                                | Delete  | Inside the signup transaction (entities are declared now)               |
| `PluginInstallationWorkflow`                                                                                                                           | Installs a plugin                                              | Delete  | One transaction; a summary rebuild, if any, is a job                    |
| Two helpers in `platform/workflow/interruption.ts`                                                                                                     | Interrupt an execution by name                                 | Delete  | Cancelling a job is an `UPDATE`                                         |
| `BackgroundWorkWorkflow`                                                                                                                               | Generic background work                                        | Job     | The job table itself                                                    |
| `AutomationRunWorkflow`                                                                                                                                | After-hook runs                                                | Job     | A job per hook run                                                      |
| `FrequentCronWorkflow`                                                                                                                                 | Periodic tick                                                  | Job     | A scheduler loop that inserts due jobs                                  |
| `NotificationDeliveryWorkflow`                                                                                                                         | Outgoing notification                                          | Job     | A job with attempts                                                     |
| `TranslateEntityWorkflow`, `…AttemptWorkflow`                                                                                                          | Provider translation, with retries                             | Job     | One job; attempts are a column                                          |
| `ProviderEntityPopulationWorkflow`, `…AttemptWorkflow`                                                                                                 | Fetch an entity from a provider                                | Job     | One job; attempts are a column                                          |
| `ProviderRelatedPagesWorkflow`                                                                                                                         | Follow-up provider pages                                       | Job     | Child jobs                                                              |
| `EntityImportWorkflow`                                                                                                                                 | Import one entity by provider ID                               | Job     | A job                                                                   |
| `IntegrationSyncWorkflow`, `ProcessIntegrationRunWorkflow`                                                                                             | Integration sync                                               | Job     | One job per sync run                                                    |
| `ExportBackupWorkflow`, `RestoreBackupWorkflow`                                                                                                        | Backups                                                        | Job     | A job each                                                              |
| `UserLifecycleWorkflow`                                                                                                                                | Account delete and reset                                       | Job     | A job                                                                   |
| `ScriptExecutionWorkflow`                                                                                                                              | Plugin-authored workflows with `sleep`, `child` and `activity` | Keep    | The one durable workflow plugins can write                              |
| Six import workflows (`ProcessImportRun`, `ProcessDataImport`, `…Segment`, `ProcessGenericImportChunks`, `ProcessIngestionCapture`, `CancelImportRun`) | Imports, in nested stages                                      | Merge   | One import workflow with a chunk cursor; cancelling is a flag it checks |

- Plugin-authored durable workflows are a real product feature, so a durable engine with deterministic
  replay stays, used only by plugin workflows and imports.
- The job table needs `kind`, `payload`, `run_at`, `attempts`, `locked_until`, `priority`, `depth`, a
  coalescing key and a result. Claiming with `SKIP LOCKED` keeps it safe with replicas (rule 2).

## Tables

The kernel has 93 tables and 19 views. About 63 tables and none of the views are needed. Nearly all the
cuts are in execution bookkeeping, derived state, imports and plugin state. The product's own data (auth,
entities, events, relationships, definitions) stays as it is.

| Area                 | Now | After | What changes                                                                                                                                                                                                                                                                                                                                   |
| -------------------- | --: | ----: | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Auth and OAuth       |  15 |    15 | Nothing. These belong to the auth library and to the OAuth provider for API clients                                                                                                                                                                                                                                                            |
| Domain data          |  13 |    13 | Nothing, apart from checking whether `event_scope`, a per-user, per-entity revision counter, can become a column                                                                                                                                                                                                                               |
| Definitions          |  11 |    11 | Keep them as immutable rows per revision, because data references them. Delete the 19 `user_*` and `global_*` views: the catalog is resolved in memory from installations and cached revisions                                                                                                                                                 |
| Plugins              |   9 |     5 | Fold `plugin_revision_manifest` into `plugin_revision` and `user_plugin_state` into `plugin_installation`. Delete `plugin_uninstall_receipt` (uninstalling is a transaction) and `plugin_catalog_change` (a catalog version column on `user`)                                                                                                  |
| Scripts              |   4 |     3 | Delete `sandbox_workflow_reference`: a job or workflow row already names its script                                                                                                                                                                                                                                                            |
| Execution            |  11 |     4 | Keep `workflow_execution` and `workflow_step`, for plugin workflows and imports. Add `job` and `idempotency_key`. Delete `workflow_runner`, `background_work`, `automation_run`, `automation_run_attempt`, `automation_trigger`, `automation_trigger_recipient`, `mutation_receipt`, `signal_schedule_delivery` and `user_lifecycle_operation` |
| Derived state        |   9 |     1 | Event streams, stream bindings and stream work, relationship projections, their bindings and work, `event_projection` and `relationship_sync_generation` become one `derived_value` table: subject, kind, plugin revision, value and source revision. `entity_enrichment_request` becomes a job                                                |
| Imports              |  11 |     5 | Keep `import_run` (with a cursor), `import_issue`, `import_activity` and `integration`. `import_batch`, `import_capture`, `import_payload_reservation` and `data_import_submission` merge into one `import_item`. `integration_auto_disable_claim` becomes a column, and `provider_import_admission` a coalesced job                           |
| Backups              |   4 |     1 | The three staging tables go if a restore runs in one transaction. The backup memory test decides it                                                                                                                                                                                                                                            |
| Notifications        |   4 |     3 | `notification_delivery` becomes a job                                                                                                                                                                                                                                                                                                          |
| V1 migration reports |   2 |     2 | Keep                                                                                                                                                                                                                                                                                                                                           |
| **Total**            |  93 |    63 | And 0 views instead of 19                                                                                                                                                                                                                                                                                                                      |

`mutation_receipt` shows the pattern. It has 24 columns, pinning the plugin revision, config revision,
script, account generation, input fingerprint, dispatch and evidence on every item, and the `full11` run
wrote 67,235 receipts for about 9,000 domain rows.

## Cross-cutting mechanisms

Of the 11 mechanisms that run through the kernel, 1 stays, 4 are deleted and 6 merge into the job table, a
derived-value fold or a plain query. Together they make up most of the vocabulary that makes the code feel
heavy.

| Mechanism                                         | What it guards now                                                                                                                                                 | Size                                                                                     | Verdict | Becomes                                                                                                                                                                                   |
| ------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------- | ------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Mutation receipts                                 | Exactly-once for every script-driven write, with 24 columns of provenance per item                                                                                 | `receipt` 1,182 mentions in 65 files; `receipts.ts` 786 lines                            | Delete  | Natural-key upserts (rule 3), plus an `idempotency_key` row for the four request kinds in [`idempotency.md`](idempotency.md)                                                              |
| Account generations                               | A token on `user` that every import, receipt, workflow and socket ticket carries, so work started before a reset can't write after it                              | `accountGeneration` in 40+ files                                                         | Delete  | Reset and delete lock the `user` row and delete the user's jobs in one transaction. A job's transaction takes a share lock on that row, so it either finishes first or finds its job gone |
| Admission                                         | Backpressure and rate limits: provider HTTP tickets in Redis, a 50-item provider import backlog, notification and data-import admission                            | `admission` 369 mentions; HTTP admission and dispatcher are 1,632 lines                  | Merge   | A per-kind concurrency limit on the job table, and one rate-limit row per provider host (`next_allowed_at`, updated atomically)                                                           |
| Leases and claims                                 | Ownership of in-flight work: workflow runners, fair-queue locks renewed every 30 s, import, upload and OAuth refresh leases, stream and projection claims          | `lease` 426 and `claim` 439 mentions                                                     | Merge   | `job.locked_until` claimed with `SKIP LOCKED`. An OAuth refresh is a row lock inside its transaction                                                                                      |
| Fair queue                                        | Interactive and background lanes in Redis, with a starvation limit                                                                                                 | `fair-queue-store.ts` 724 lines                                                          | Merge   | A `priority` column; claim in `priority, run_at` order                                                                                                                                    |
| Wake-ups                                          | Redis pub/sub and engine wake-ups, so a waiting request or worker resumes quickly                                                                                  | Workflow engine and execution notifications                                              | Delete  | Requests no longer wait on workflows (rule 4). Workers use `LISTEN/NOTIFY` on job insert, with a short poll as backstop                                                                   |
| Lifecycle batches and triggers                    | Fan-out of after-hooks: a trigger tree with depth and recipients, chunked to half the sandbox context                                                              | Automations module, 5,963 lines                                                          | Merge   | After commit, one job per (installation, hook) holding the changed IDs. A `depth` column stops loops                                                                                      |
| Event streams, projections and history correction | Four separate ways to derive state: checkpointed stream processors, relationship projections, event projections, and the history-correction state machine in Media | Stream code 1,503 lines, projections 1,018, history correction about 1,700 in the plugin | Merge   | One derived-value fold per subject, declared by the plugin and computed in the writing transaction (rule 5). Only histories over a size cap fall back to a job                            |
| Sync generations                                  | Mark-and-sweep of relationships an integration sync no longer sees                                                                                                 | `relationship.syncGeneration` and its table                                              | Merge   | A set difference in one `DELETE … WHERE NOT IN` inside the sync's transaction                                                                                                             |
| Redis                                             | Socket tickets, fair queue, replay journal, entity-interest sessions, upload intents, search cache                                                                 | 28 non-test files                                                                        | Delete  | The job table for the queue, `workflow_step` for the journal, an in-process LRU for the search cache, and [`entity-updates.md`](entity-updates.md) for the socket                         |
| Plugin revision pins                              | Which plugin revision a write or a run uses                                                                                                                        | `pin` 1,121 mentions                                                                     | Keep    | One column, `plugin_installation.revision_id`, read once per transaction. A job or workflow stores the revision it started with                                                           |
