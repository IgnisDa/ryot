# Invoke an Authenticated Operation

**Parent Plan:** [Web Client Plugin Tracer](./README.md)

**Status:** done

## What to build

Add one real authenticated fixture operation that can be invoked from the mounted client plugin. A user action in the fixture sends a typed request through the explicit `RyotClient` supplied by `@ryot/client-sdk/react` inside the one per-session plugin runtime from `@ryot/client-sdk/plugin`; the kernel executes it through the existing authenticated app client for the bridge session's installation, and the typed result returns to the fixture. The plugin document never receives the Better Auth cookie, API key, or another reusable Ryot credential.

Keep authority in kernel-owned bridge session state. The plugin request supplies an operation slug and operation input, not a trusted plugin ID, installation ID, artifact hash, server URL, or user ID. The kernel binds those values from the exact `PluginHost` session established in Task 03 and invokes only an operation belonging to that installation. Use the existing backend plugin-operation contract and authorization behavior rather than adding a client-specific backend bypass.

Add the minimum protocol version 1 request/response machinery required for concurrent calls, correlation IDs, structured success values, opaque declared platform failures, unexpected transport failures, and runtime disposal rejection. The fixture UI must exercise a successful call and a stable failure branch without displaying internal causes. Query and operation pending calls must be owned by the same per-session runtime and single dispatcher. Keep this operation slice focused: do not add unscoped data methods, storage, subscriptions, or native capabilities; the completed shared runtime record defines the recipe-backed query and React query/mutation surface.

## Acceptance criteria

- [x] The fixture manifest declares one backend operation and its client home invokes it through a typed client SDK method.
- [x] The request crosses the production iframe `MessagePort`, kernel authenticated app client, existing backend operation route, and backend plugin runtime before returning a result.
- [x] The bridge session, not plugin-controlled request data, supplies server, user, plugin, installation, package, and artifact identity.
- [x] A plugin cannot use the operation method to invoke another installation's operation or substitute another installation ID.
- [x] The plugin document receives no Ryot cookie, API key, bearer token, or reusable operation credential.
- [x] Multiple in-flight calls are correlated correctly and settle once.
- [x] Declared backend/platform failures are represented by opaque `operation-failed` SDK errors; expected plugin business outcomes are typed successful values, and transport and malformed-result failures remain distinguishable without leaking internal diagnostics into normal UI.
- [x] Closing or replacing the bridge disposes the shared runtime, rejects pending calls exactly once, and releases request bookkeeping.
- [x] The fixture renders an accessible pending state, successful result, retry action, and stable expected-error state using the client UI SDK.
- [x] Backend authorization/integration tests, bridge protocol tests, SDK tests, and browser interaction tests cover success, expected failure, identity spoofing, teardown, and credential isolation; all earlier tracer tests still pass.

## Implementation Notes

- **`ryot.operations.invoke({ slug, input, output })` is the plugin operation surface.** The explicit `RyotClient` supplied to the per-session plugin runtime carries the `operations` category. `ryot.navigation.push/replace` is the shared navigation surface; `PluginLink` and the reactive location, params, and search hooks remain plugin React conveniences backed by the same runtime. All categories still share the runtime's single dispatcher and disposal path.
- **`Schema` is part of the client SDK ABI.** `ryot.operations.invoke` takes an `output` codec because the wire value is genuinely `unknown` on the client and nothing else validates it. Plugin source imports `Schema` from `@ryot/client-sdk/effect`, which re-exports `Schema` and nothing else, mirroring `@ryot/sandbox-sdk/effect` for backend scripts. Bare `effect` imports remain untrusted, so there is one approved ABI surface rather than two.
- **There is no input codec.** The sandbox already validates operation input and answers with a typed `PluginInvocationError` carrying `phase: "input"`. A second client-side declaration would be a mirror that can drift.
- **Identity is structurally unforgeable, not merely validated.** Three layers stack. `PluginBridgeOperationRequest` is a `strictStruct`, so a request smuggling `pluginSlug`, `installationId`, `userId`, or `scope` fails to decode and is dropped. The bridge then builds `{ input, operationSlug }` from two named decoded fields rather than passing the wire object on. Finally `PluginOperationsService.invoke` takes `{ scope, pluginSlug, request }` and reads `invocation.request.*` separately — the first pass instead called `service.invoke({ ...request, scope, pluginSlug })`, where a future reordering of the spread would silently have let plugin data supply the slug. `PluginOperationRequest = Pick<PluginBridgeOperationRequest, "input" | "operationSlug">` has no slug field at all, so that regression is now inexpressible. Review confirmed no `...request` / `...invocation` / `...event.data` / `Object.assign` remains anywhere in the plugin modules, and `{ ...outcome, requestId, type }` puts kernel-owned keys after the spread so a malformed outcome cannot forge them either.
- **Only `outcome` and `reason` cross the port.** `PluginInvocationError` diagnostics carry sandbox messages with line and column numbers; they are collapsed to the literal `"operation-failed"` in the kernel. `AuthenticatedApiError.cause` is discarded and never logged. `scope.userId` never reaches the wire — the backend derives the user from the cookie. The compiled `plugin.js` contains no `cookie`, `x-api-key`, or `Authorization` string; its only `credentials` hits are React DOM's `crossOrigin="use-credentials"` handling.
- **Failure classification reads the contract, not a tag list.** `Schema.is(Schema.Union([AuthUnauthorized, AuthRateLimited, PluginNotFoundError, PluginRequestError, PluginInvocationError]))` is exactly the declared error set of the `plugins.invoke` endpoint, so the union cannot drift from the contract the way a hand-written list of `_tag` strings would. `Schema.is` was verified to work on real instances of those `Schema.TaggedError` classes, so no `instanceof` fallback was needed. Anything else — a 500, an HTML error page, a CORS failure, a response decode failure — falls through to `"transport"`. `AuthUnauthorized` classifies as `"operation-failed"`: it is a declared backend failure, and plugin code should not be the thing that drives re-authentication.
- **Aborting really aborts.** The chain `runtime.runPromise({ signal }) -> Effect.tryPromise(signal) -> runContract -> FetchHttpClient` was driven against a local server and aborting the outer signal fired `request.signal`'s abort event server-side. It is a true abort, not a detach.
- **Two settle-once bugs were fixed after review.** A non-cloneable `input` (a function, symbol, or `WeakMap`) made `port.postMessage` throw inside the promise executor _after_ the pending entry was stored, so a raw `DataCloneError` escaped the SDK ABI and the entry leaked for the life of the document. `postMessage` is now wrapped, and the catch deletes the entry before rejecting with `RyotClientError("transport")`. Separately, a plugin can omit the required `input` at runtime because the compiler strips types without typechecking plugin source. The SDK now rejects omitted or non-JSON input locally with `RyotClientError("invalid-input")` before adapter dispatch; a no-input operation must send explicit JSON `null`.
- **The live region has to pre-exist the text.** The first pass mounted and unmounted four mutually exclusive `StatusMessage` nodes. A `role="status"` element inserted together with its text is the classic live-region pitfall: assistive technology has no pre-existing region to observe changing, so the pending and success states — the two the criteria name first — were the two likely to be silent, while `role="alert"` would have announced on insertion. The fixture now renders exactly one always-mounted `StatusMessage` whose tone and text come from lookup records, and a `@ryot/client-ui-sdk` test pins the contract the fixture depends on: the same element instance survives a pending -> success -> error tone change. An `aria-busy` on the surrounding `<section>` was tried and removed — Core-AAM inherits `aria-busy` from the nearest ancestor that specifies it, so it would have suppressed the very pending announcement the fix was for.
- **Pending limit and operation scope.** Operation and RyotQL pending requests share an aggregate maximum of 64 per session, enforced by both the SDK and kernel. Exceeding it is a protocol failure through the existing wire `failed` and public `protocol` teardown; requests are not queued or retried, and no new error reason is introduced. Operation calls have no operation-specific timeout, automatic retry, or cache. Recipe queries use the shared React query surface, including its `AbortSignal` path, SWR refresh, and five-minute idle TTL.
- **Known gaps.** The fixture's own `client/home.tsx` has no test, because `plugins/fixture` has no test runner and adding one is package infrastructure beyond this slice; its two halves are covered instead by the SDK operation tests and the UI SDK primitive tests, which is the same disposition Task 04 took for the fixture router. Criterion 2 is verified hop by hop rather than end to end in a real browser: no browser-driver harness exists, and jsdom drops the `postMessage` transfer list, which is why Task 04 extracted the transport-agnostic bridge in the first place. The completed shared runtime rejects plugin-side pending calls during the protocol version 1 terminal lifecycle before the port and iframe are released, and the later completed tasks reuse that ordering.
- **Separate backend item, not a defect of this slice.** `auth: "integration"` operations resolve their scope from the caller's payload via `getByIdAnyUser`, so holding an `integrationId` is what authorises acting as its owner. This is a deliberate bearer-capability design — the id is a random `generateId()` value, the same shape as the unauthenticated content-addressed artifact route — and review confirmed nothing in this slice can leak one to a plugin document. The fixture's `greet` is `auth: "user"` and unaffected. Recorded here because this slice is the first thing that lets plugin client code aim payloads at operation slugs at all.
