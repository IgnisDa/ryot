# Ryot Client Loading Follow-up Implementation Plan

## Context

Implement against `ultra-rewrite` at current head.

The previous client-loading refactor was successful:

- Plugin archives now contain precompiled client modules.
- Client runtime and kernel renderer modules are built during server/image assembly.
- Navigation no longer invokes Vite or the client compiler.
- `client-pages/prepare` is now a few hundred milliseconds instead of multiple seconds.
- Saved-view preparation no longer has the extra record lookup.
- Artifact sessions are gone.
- Static files no longer reconstruct client graphs.
- Same-artifact page changes can reuse an iframe and replace its document context.
- Catalog connection no longer causes an unnecessary catalog refetch.

The remaining cold-load bottleneck is static module delivery. A composed page currently physically embeds copies of the shared runtime, plugin modules and renderer modules under a page-specific grant URL. Consequently:

- identical runtime files have different URLs in different page compositions;
- Cloudflare/browser caches cannot reuse them effectively across compositions;
- the first iframe has a large module waterfall;
- all automatic entity-presentation modules are imported eagerly even when unused.

The next architecture must make compiled code artifacts independently cacheable while retaining authorization for private code.

---

# Fixed product and architecture decisions

These decisions are final and must not be reopened during implementation.

### Plugin archive trust

Installing a plugin archive means trusting its compiled client executable code.

The server must continue validating:

- archive structure;
- artifact format/version;
- content hashes;
- file/path limits;
- MIME types;
- manifest consistency.

The server does **not** need to reproduce the plugin's compilation or prove that the executable was generated by `ryot plugin build`.

Document this trust boundary explicitly.

### Public versus authorized code

The following image-owned code may be anonymously retrievable and publicly cached:

- the shared client runtime;
- kernel renderer artifacts;
- client artifacts belonging to plugins shipped in the Ryot server image.

Everything else remains authorization protected, including:

- user-owned/private plugins;
- system plugins installed into the running server rather than shipped in the image.

If an artifact hash is both present in a public image artifact and referenced by an otherwise private plugin, the bytes are already public and may use public access.

### One artifact-serving architecture

There must **not** be separate system-plugin and user-plugin routes, services, repositories, or URL structures.

Use one generic content-addressed asset route for every compiled client artifact.

Use this route shape:

```text
/api/client-assets/:artifactHash/:accessKey/*
```

`accessKey` is:

```text
public
```

for image-public artifacts, or a random capability token for authorized artifacts.

Examples:

```text
/api/client-assets/<hash>/public/module.js

/api/client-assets/<hash>/<private-grant-token>/module.js
```

This is one route and one implementation. Plugin ownership must not appear in the path.

The access segment is deliberately part of the directory path rather than a query parameter so relative imports and CSS URLs inherit it:

```text
.../<hash>/<accessKey>/module.js
→ ./chunk-x.js
→ .../<hash>/<accessKey>/chunk-x.js
```

Do not create `/system`, `/user`, `/private`, `/shipped`, or similar route variants.

### Dynamic composition documents

A composed iframe's HTML is no longer an immutable compiled artifact.

Store an immutable **client page composition manifest**, then generate its small HTML document when the iframe requests it.

Preparation returns a short-lived document capability. The iframe uses it to load:

```text
/api/client-pages/documents/:token
```

The server:

1. resolves the document grant;
2. loads the immutable composition manifest;
3. issues/reuses access grants for authorized code artifacts;
4. substitutes concrete public/private asset URLs;
5. emits the import map, preload links, stylesheets, composition descriptor and bootstrap module.

The HTML response is:

```text
Cache-Control: private, no-store
```

The referenced compiled JS/CSS/font/image/WASM files remain immutable and cacheable.

### Automatic entity presentations

Automatic presentations become lazy.

Image-public presentation code is genuinely lazy:

- no JS request before the presentation is required;
- no presentation CSS before it is required;
- first use may show a presentation-loading state;
- successful loads remain cached for the iframe runtime.

Authorized presentation code remains _logically_ lazy but is warmed while its grant is valid:

- JS closure is module-preloaded;
- CSS is loaded;
- remaining artifact assets are preloaded;
- the presentation module is **not evaluated/imported** until required.

This avoids grant-renewal machinery while keeping executable evaluation lazy.

### Page state

Different prepared documents using the same composition reuse the iframe/runtime but mount a fresh page React tree.

Do not add arbitrary page-local state restoration.

Composition-runtime state such as already-loaded lazy presentation modules may survive document replacement.

### Existing update behavior

Keep the existing explicit:

```text
Update available
→ Reload updated page
```

behavior.

Never destructively replace a running page because the catalog changed.

# Target terminology

Keep **artifact** for immutable compiled code/assets.

Stop calling a complete runnable page an artifact.

Use these concepts consistently:

```text
Client artifact
    Immutable compiled JS/CSS/assets.
    Identified by artifactHash.

Client composition
    Immutable description of one runnable iframe application.
    Identified by compositionHash.

Client document
    Small dynamic HTML representation of a composition for one authorized user.

Document grant
    Short-lived capability to retrieve a client document.

Artifact grant
    Short-lived capability to retrieve one non-public client artifact.
```

Rename current page-build/page-artifact terminology accordingly.

In particular:

```text
ClientPageBuildService
→ ClientPageCompositionService

client_page_build
→ client_page_composition

ClientPageArtifactIdentity
→ ClientPageCompositionIdentity

artifactKey on page identities
→ compositionKey

artifactHash on prepared page / bridge runtime
→ compositionHash
```

Do not retain aliases for the old terminology.

The compiled plugin/archive artifact types themselves do not need a gratuitous rename as part of this work unless the rename naturally falls out of the refactor. The important correction is that a _page composition_ must no longer masquerade as a compiled artifact.

# Phase 1 — Introduce a generic client-artifact backend module

Create a generic backend module, conceptually:

```text
kernel/backend/src/modules/client-artifacts/
```

It owns generic compiled-client-artifact persistence, lookup, access policy and serving.

Move the current client artifact tables out of plugin-specific ownership.

Because there is no production data, directly rename/rebuild the schema rather than introducing migrations that copy or bridge old rows.

Conceptually:

```text
client_artifact
    hash PK
    format
    api_version
    bridge_version
    compiler_version

client_artifact_file
    artifact_hash
    name
    content_type
    contents
    PK (artifact_hash, name)
```

`plugin_revision.client_artifact_hash` remains a FK to the generic artifact table.

Move these repository responsibilities out of `PluginRepository`:

```text
persistClientArtifact
loadClientArtifact
findArtifactFile
artifact metadata/file listing
```

into a `ClientArtifactsRepository`.

`PluginRepository.persist()` should depend on this generic repository and persist the archive-provided client artifact through it inside the caller's existing transaction.

This satisfies the backend rule that one repository owns each table and gives client pages and plugin ingestion one shared primitive.

No duplicated artifact storage implementation is allowed.

# Phase 2 — Replace the image artifact files with one image-client manifest

Today assembly writes:

```text
client-runtime.json
kernel-renderers.json
```

Replace these with one build-generated file, for example:

```text
client-image.json
```

Its schema should contain:

```text
runtime:
    artifact
    entry map

kernel renderers:
    name
    sourceHash
    artifact

public artifact hashes:
    runtime artifact hash
    all kernel renderer artifact hashes
    all compiled-client artifact hashes from shipped plugin archives
```

`apps/server/scripts/assemble.ts` already knows the shipped plugin archive set.

While assembling, read those archives and collect their `compiledClient.hash` values.

Do **not** duplicate shipped plugin artifact bytes into `client-image.json`; their archives already contain those bytes and ingestion persists them normally. Only record their hashes as public.

Runtime and kernel artifacts still need their bytes in the image manifest because they are not plugin revisions in the database.

Replace `ImageClientArtifacts` with a generic image-backed client-artifact service under the new client-artifacts module.

At startup it should construct:

```text
imageArtifactsByHash
publicArtifactHashes
runtime descriptor
kernel-renderer descriptors
```

Assert duplicate hashes are byte-for-byte/metadata identical. Treat a hash collision with different immutable contents as a fatal startup invariant failure.

Update `apps/server/AGENTS.md` to describe this single image manifest.

# Phase 3 — Build the unified artifact store and access service

Create one generic `ClientArtifactStore`.

It should expose roughly:

```text
describe(hash)
findFile(hash, fileName)
exists(hash)
isPublic(hash)
```

`describe()` returns metadata plus the list of file names/content types without loading every file body.

Lookup rules:

```text
if hash exists in imageArtifactsByHash:
    use the in-memory image artifact

otherwise:
    use ClientArtifactsRepository
```

Publicness is independent from storage location:

```text
isPublic(hash) = publicArtifactHashes.has(hash)
```

A shipped plugin artifact may therefore be stored in PostgreSQL but still be public because its hash came from the immutable image manifest.

This is intentional.

Do not inspect plugin scope (`system` versus `user`) in this service.

# Phase 4 — Generalize capability-grant plumbing

There will now be two kinds of short-lived capabilities:

```text
document grant:
    userId + compositionHash

artifact grant:
    userId + artifactHash
```

Both require the same behavior:

- random 32-byte base64url token;
- only hashed token stored as the lookup key;
- reusable token keyed by `(user, target)`;
- TTL;
- NX creation;
- stale reusable-token cleanup;
- strict token validation.

Extract the reusable Redis capability mechanics into one internal infrastructure primitive.

Domain services still own their schemas and key namespaces. Do **not** make document and artifact grants interchangeable.

For example:

```text
ReusableCapabilityGrantStore
    issue(...)
    resolve(...)
```

with:

```text
ClientDocumentGrantService
ClientArtifactGrantService
```

wrapping it.

Keep the existing approximately 15-minute grant TTL unless a test demonstrates an implementation problem.

Artifact grants are stable for `(userId, artifactHash)` for their lifetime so multiple page compositions within that window produce exactly the same authorized artifact URL.

# Phase 5 — Add the single client-asset route

Replace the current page-artifact wildcard endpoint with:

```text
GET /client-assets/:artifactHash/:accessKey/*
```

Do not apply normal authenticated HTTP middleware. Authorization is the capability itself.

Request handling:

```text
validate artifactHash
validate canonical file path

if accessKey == "public":
    require ClientArtifactStore.isPublic(artifactHash)
else:
    resolve artifact grant
    require grant.artifactHash == artifactHash

load file from ClientArtifactStore
return file
```

A grant for artifact A must never permit reading artifact B by changing the URL hash.

Continue canonical/path traversal rejection, including encoded traversal variants.

Headers for public artifacts:

```text
Cache-Control: public, max-age=31536000, immutable
Access-Control-Allow-Origin: *
Cross-Origin-Resource-Policy: cross-origin
X-Content-Type-Options: nosniff
Referrer-Policy: no-referrer
```

Headers for authorized artifacts:

```text
Cache-Control: private, max-age=31536000, immutable
Access-Control-Allow-Origin: *
Cross-Origin-Resource-Policy: cross-origin
X-Content-Type-Options: nosniff
Referrer-Policy: no-referrer
```

Do not make grant expiry invalidate bytes already present in the user's browser cache. A user who was previously authorized to execute code may retain those previously received immutable bytes.

Do not perform catalog, installation, saved-view or page-currentness checks while serving asset files.

# Phase 6 — Replace page builds with composition manifests

Rewrite the current page-build abstraction around immutable compositions.

Schema:

```text
client_page_composition
    composition_key PK
    composition_hash UNIQUE
    identity JSONB
    manifest JSONB
    created_at
```

There is no `artifact_hash` FK because a composition is no longer a copied client artifact.

Define schemas for:

```text
ClientPageCompositionIdentity
ClientPageCompositionManifest
ClientArtifactFileReference
ClientCompositionModuleReference
ClientCompositionPresentationRegistration
```

A file reference is structural, not a URL:

```text
{
    artifactHash,
    file
}
```

Concrete URLs are generated only when serving a document.

Extend the plugin runtime/revision metadata used by graph resolution so each client-capable plugin exposes its persisted:

```text
clientArtifactHash
```

A plugin composition contributor should contain at least:

```text
pluginId
pluginSlug
sourceHash
clientArtifactHash
namespace
exports
pluginDependencies
```

Kernel renderer contributors should likewise contain their image artifact hash.

The composition identity must include the runtime artifact hash.

This ensures a new server image/runtime automatically produces a new composition identity even if someone forgets to bump an unrelated source hash.

Installation IDs must **not** enter composition identity.

They remain runtime authorization/operation identity only.

# Phase 7 — Explicitly classify eager versus presentation-only contributors

The graph resolver currently lets automatic presentation registration pull every presentation plugin into the same undifferentiated contributor set.

Change it to retain two concepts:

```text
eager contributor closure
presentation-only contributor closure
```

The eager closure contains:

- the primary page/plugin-route module;
- its declared plugin dependencies;
- kernel renderer artifact when applicable.

Automatic presentation discovery may add additional contributors, but those remain presentation-only unless already present in the eager closure.

For every presentation registration, retain its transitive artifact dependency closure.

Example:

```text
presentation:
    ownerPluginId
    entitySchemaSlug
    layout
    module:
        specifier
        binding
    artifactClosure:
        [artifactHashA, artifactHashB, ...]
```

`artifactClosure` is needed because a lazy presentation plugin can statically import another plugin's module and may require its CSS.

Eager wins over lazy. If an artifact participates in both sets, treat it as eager.

Preserve deterministic ordering everywhere before hashing.

# Phase 8 — Build immutable composition manifests without copying bytes

Rename `ClientPageBuildService` to `ClientPageCompositionService`.

`materialize()` must:

1. resolve the composition identity;
2. verify every referenced code artifact exists;
3. construct the composition manifest;
4. hash its canonical representation;
5. persist the immutable composition row;
6. validate an existing row on conflict.

It must **not**:

- invoke the compiler;
- invoke Vite;
- copy runtime files;
- copy plugin files;
- copy renderer files;
- create a synthetic `index.html`;
- persist a new client code artifact.

The manifest should contain enough information to generate the document:

```text
runtime artifact + bootstrap entry
runtime import-map entry references

plugin/kernel import-map mappings
application descriptor
route registry
automatic presentation registry

eager artifact set
eager stylesheet references

lazy presentation dependency closures
```

Keep `compositionKey` as the lookup hash derived from the resolved composition identity.

Use `compositionHash` for the canonical manifest hash and runtime identity.

On conflict:

```text
same compositionKey + different identity/manifest/hash
→ fatal invariant violation
```

# Phase 9 — Keep lifecycle materialization, but make it composition-only

The existing lifecycle decision remains correct:

```text
plugin/catalog mutation
→ materialize required compositions
→ expose/invalidate the new catalog state
```

Keep materialization at:

- server/system baseline startup;
- user bootstrap;
- private plugin install;
- private plugin update;
- plugin enable/disable/config transitions when they affect the effective graph;
- system plugin ingestion/update/removal;
- generated saved-view changes that change renderer/code identity.

Saved-view changes that affect only:

- name;
- icon;
- data sources;
- renderer settings;
- layout preferences;

must not create a new code composition unless their renderer/dependency identity actually changes.

Rename methods:

```text
materializeUser
→ materializeUserCompositions

materializeSystemBaseline
→ materializeSystemCompositions

assertUserBuilds
→ assertUserCompositions
```

Remove `CLIENT_PLUGIN_COMPILER_LIMITS.concurrency` from this runtime path.

Use a local bounded composition-materialization concurrency such as `8`, or an existing generic DB-work concurrency primitive if one already fits.

Do not retain a compiler dependency merely to import its concurrency limit.

# Phase 10 — Make preparation composition-only

`ClientPagesService.prepare` remains side-effect free.

Flow:

```text
resolve current target
→ resolve current composition identity/key
→ require already-materialized composition
→ construct runtime/page identity
→ issue/reuse document grant
→ return
```

Missing composition is an invariant failure.

Do not add a fallback materialization path.

Prepared page output should change from:

```text
artifact: {
    hash,
    grant,
    ...
}
```

to terminology such as:

```text
composition: {
    hash,
    format,
    apiVersion,
    bridgeVersion,
    compilerVersion,
    documentGrant: {
        src,
        grantId,
        expiresAt
    }
}
```

`src` points to:

```text
/api/client-pages/documents/:token
```

The document grant payload contains:

```text
userId
compositionHash
```

Do not store the entire prepared page or graph in Redis.

Page context still crosses the bridge separately.

# Phase 11 — Dynamically render client documents

Add:

```text
GET /client-pages/documents/:token
```

This is a capability route and does not require normal request authentication.

Handling:

```text
resolve document grant
→ load composition by compositionHash
→ collect unique referenced artifact hashes
→ resolve access URL for each artifact
→ generate import map
→ generate eager preload/style tags
→ generate authorized-lazy warming tags
→ serialize concrete composition descriptor
→ render small HTML document
```

For each artifact:

```text
if image-public:
    accessKey = "public"
else:
    accessKey = ClientArtifactGrantService.issue(userId, hash)
```

All callers use the same URL builder:

```text
/client-assets/<hash>/<accessKey>/<file>
```

There must be one shared URL-generation primitive. Do not construct this path ad hoc in multiple modules.

HTML response:

```text
Cache-Control: private, no-store
Content-Security-Policy: sandbox allow-scripts
Referrer-Policy: no-referrer
X-Content-Type-Options: nosniff
```

Also include:

```html
<meta name="referrer" content="no-referrer" />
```

The document must use absolute asset paths so its own capability URL never becomes part of static asset resolution.

# Phase 12 — Define document preload behavior centrally

Implement one pure preload planner.

Input:

```text
composition manifest
artifact descriptions
artifact access modes
```

Output:

```text
modulepreload URLs
stylesheet URLs
other preload URLs
lazy presentation stylesheet URLs
```

Deduplicate every URL.

Do not scatter MIME/preload decisions across HTML rendering code.

## Eager artifacts

For the runtime and all eager application artifacts:

- module-preload their JavaScript files;
- load required CSS with `rel=stylesheet`;
- preload useful fonts/WASM/assets based on MIME.

For the shared runtime, preload its complete emitted JavaScript graph on a cold iframe.

The objective here is to turn the current serial discovery waterfall into parallel requests.

Do **not** implement clever data-URL facades, custom module loaders, or package-specific bundler hacks to reduce the number of runtime entry modules.

One ESM namespace per public import specifier is legitimate. Once these resources have stable public URLs and are CDN/browser-cacheable, request count alone is not a reason to create bundler complexity.

## Public lazy presentation artifacts

If an artifact is only needed by an automatic presentation and is image-public:

```text
no modulepreload
no stylesheet
no asset preload
```

before first use.

## Authorized lazy presentation artifacts

If an artifact occurs in a lazy presentation dependency closure and is not public:

warm **all files in the artifact** while the grant is valid.

Use:

- `modulepreload` for JavaScript;
- actual `stylesheet` links for CSS;
- suitable `preload` links for fonts/images/WASM/other supported static assets.

The JavaScript module must not be imported/evaluated at this point.

This guarantees that later lazy evaluation can use the document module map/cache without needing a still-valid network capability.

Do this per artifact, not per ownership type.

A non-image system plugin and a user plugin therefore run through the exact same warming implementation.

# Phase 13 — Change the bootstrap composition descriptor for lazy presentations

Today the generated bootstrap eagerly loads:

```text
page/route modules
+
every automatic presentation module
```

Change that.

The initial module reference set must contain only what is required to start the application.

Automatic registry entries become lazy definitions.

Conceptually:

```text
{
    ownerPluginId,
    entitySchemaSlug,
    layout,
    module: {
        specifier,
        binding
    },
    stylesheets: [...]
}
```

The dynamic HTML renderer resolves `stylesheets` to concrete URLs.

Bootstrap should maintain shared caches:

```text
modulePromisesBySpecifier
stylesheetPromisesByUrl
```

Presentation loader:

```text
await load required lazy stylesheets
module = await import(specifier)
return module[binding]
```

Validate the binding before returning it.

A presentation module belonging to an already-eager artifact naturally resolves from the existing browser module map without another network load.

# Phase 14 — Make the SDK presentation registry asynchronous

Change `EntityPresentationRegistration` from an eagerly supplied definition to a loader.

Conceptually:

```text
{
    ownerPluginId,
    entitySchemaSlug,
    layout,
    load: () => Promise<EntityPresentationDefinition>
}
```

The presentation registry owns per-registration state:

```text
idle
loading
ready
failed
```

Requirements:

- multiple entities requiring the same registration trigger exactly one loader promise;
- successful definitions remain cached for the iframe composition lifetime;
- document replacement does not discard the loaded definition;
- page React trees still remount normally;
- the existing batch query scheduler is created only after the definition has loaded;
- no entity data query runs before the presentation definition is ready.

Entity behavior:

```text
no registration
→ GenericEntityCard

registered + loading
→ layout-appropriate loading placeholder

registered + ready
→ existing PresentedEntity flow

registered + module-load failure
→ stable presentation-unavailable fallback with the basic entity link
```

Do not repeatedly attempt a failed ESM import on every React render.

A new iframe/document may try again naturally.

Keep existing component-error handling and data-query retries once a presentation has successfully loaded.

# Phase 15 — Lazy-load public presentation styles

Add a small stylesheet loader shared by the plugin bootstrap/runtime:

```text
loadStylesheet(href)
```

Requirements:

- append one `<link rel="stylesheet">`;
- resolve on `load`;
- reject on `error`;
- dedupe concurrent requests;
- cache successful loads;
- recognize an already-present eager/warmed stylesheet;
- never insert duplicate stylesheet links.

For a public lazy presentation dependency closure, load all required artifact stylesheets before resolving the presentation definition.

Authorized lazy styles are already present from document warming, so this becomes a no-op.

# Phase 17 — Make reloads obtain fresh document grants

A document grant is intentionally short-lived.

The existing local iframe reload behavior must not retry an old iframe `src` indefinitely.

On handshake/runtime failure:

```text
Retry
→ invalidate/reprepare current route
→ receive a fresh document grant
→ create a new frame generation
```

Do not simply increment the iframe key while retaining the original document URL.

The explicit catalog-update reload already uses router invalidation; use the same lifecycle.

This also avoids a hidden expiry bug when an iframe has been retained longer than the document grant TTL.

# Phase 20 — Remove the duplicate compiler build

`compileClientPluginModule()` currently calls `compileClientPlugin()` first, and `compileClientPlugin()` performs its own full Vite application build before `compileClientPluginModule()` performs another Vite module build.

That duplication is no longer justified.

Refactor the compiler into:

```text

→ one module Vite build
→ artifact validation/finalization
```

Extract semantic/source-policy/type validation from the full application compiler.

`compileClientPluginModule()` should perform:

```text
plan
source limits/policy
TypeScript semantic validation
public export validation
single Vite module build
artifact validation
```

Remove the old final-page/contributor-graph compiler mode.

Specifically remove obsolete concepts such as:

```text
ClientPluginCompilerGraphInput
planGraph
graphValidationSource
server-generated compilerInput
final page application compilation
```

if they have no remaining production caller after the composition refactor.

Do not preserve them as compatibility APIs.

Retain only compiler functionality actually required for:

- plugin archive client modules;
- server-image runtime build;
- kernel renderer build.

Update compiler tests around the resulting simpler pipeline.

# Phase 21 — Ensure compiler packages are build-time only

After deleting graph compilation from runtime paths, inspect the final production server dependency graph.

`kernel/backend` should not depend on the client plugin compiler merely for:

- compiler input types;
- compiler limits;
- graph construction;
- materialization.

Move composition-specific schemas/constants into the contract or composition modules.

Do not disturb sandbox compiler/runtime dependencies; sandbox compilation is a separate system.

# Phase 22 — Freshness semantics stay page-level

Do not move freshness validation into artifact serving or document serving.

Catalog invalidation should continue to cause:

```text

→ check PreparedClientPage identity
→ current: continue
→ stale: show Update available
```

`isIdentityCurrent()` may remain relatively expensive because it runs only after meaningful catalog invalidation, not per static file.

Artifact grants and document grants are authorization/cache mechanics, not page freshness mechanics.

# Stop conditions for the implementer

Implementation should proceed without asking for routine technical decisions.

Stop and ask before continuing only if research proves one of these assumptions false:

1. The unified `/:artifactHash/:accessKey/*` route cannot safely preserve relative JS/CSS/asset references and would require ownership-specific URL structures.

2. An authorized lazy presentation cannot be made reliable for the document lifetime through eager warming/modulepreload and would require durable capabilities, grant renewal over the bridge, or making private code public.

3. Public lazy presentation loading would require changing the plugin authoring contract in a way that plugin authors must manually distinguish public/private or system/user ownership.

4. A required security property can only be achieved by exposing non-image system/user plugin code anonymously.

Do not choose one of those alternatives silently.

For anything else, make the cleanest implementation choice consistent with this plan and the repository's existing architecture rules.
